워크플로우를 플러그인으로 옮긴다. 다만 **플러그인 구조 생성·검증·테스트는 하지 않는다** — `plugin-dev:create-plugin`이 그 8단계를 이미 소유하므로, 이 스킬은 그것이 갖지 못한 앞단만 담당하고 결과를 넘긴다.

| 이 스킬이 하는 것 | create-plugin이 하는 것 |
|---|---|
| 단계 분해, 이음매/위임 판정 | 디렉토리·매니페스트 생성 |
| 스킬 조사와 협의 | 각 컴포넌트 구현 |
| 축 커버리지 설계 | plugin-validator·skill-reviewer 검증 |
| 증거 검사 설계 | 테스트·문서화 |

이 플러그인의 루트는 `${CLAUDE_PLUGIN_ROOT}` 다. references 의 명령과 경로(`scripts/…`, `templates/…`)는 전부 이 루트 기준 상대 경로로 적혀 있으므로, 실행할 때 이 루트를 앞에 붙인다 — Bash 환경에는 이 변수가 없다.

참조는 필요할 때 읽는다. `${CLAUDE_PLUGIN_ROOT}/references/` 아래 `stage-patterns.md`(이음매 판정), `axis-patterns.md`(축), `preview-patterns.md`(프리뷰), `evidence-patterns.md`(검증 6종 · 두 hook · 우회), `beads-contract.md`(bd 실측 제약), `toolchain.md`(고정 의존성).

# 0. 의존성을 확인한다

무엇이 설치돼 있는지가 **워크플로우에 무엇을 넣을 수 있는지를 바꾼다.** 없는 도구를 전제로 설계하면 생성된 워크플로우가 실행 시점에 멈춘다.

```bash
"${CLAUDE_PLUGIN_ROOT}/scripts/check-deps.sh"
```

- **필수가 빠졌으면** — `bd`, `git`, plugin-dev 플러그인, beads 플러그인, long-run 플러그인. 설치 명령을 안내하고 **여기서 멈춘다.** plugin-dev가 없으면 9단계에서 인계할 대상이 없고, beads 플러그인이 없으면 생성된 워크플로우가 세션마다 컨텍스트를 잃고, long-run이 없으면 세션 이관과 여러 세션에 걸친 실행을 맡길 곳이 없다.
- **조건부가 빠졌으면** — 그 도구에 기대는 것을 설계에서 뺀다. 있는 척하고 넣지 않는다.

  | 없는 것 | 빠지거나 막히는 것 |
  |---|---|
  | `orca` | 세션 스폰 단계와 **세션 이관 단계**. long-run 은 필수지만 `long-run:session-handoff` 는 새 orca 탭을 띄우며 폴백이 없다 — 플러그인이 설치돼 있어도 orca 없이는 그 단계가 돌지 않는다 |
  | `agent-browser` | 브라우저 검증 단계 |
  | `npx` | 4단계의 스킬 레지스트리 조사(`find-skills`)와 위임 대상 스킬 설치. 설치된 스킬만으로 설계하고, 조사하지 못했다는 사실을 스펙에 남긴다 |
  | `jq` | 5단계의 `axis-sync.sh resolve`·`ids`·`retired`. `pull`·`list`·`show` 는 된다 — 상속(`extends`)이 있는 도메인은 병합된 축을 볼 수 없으므로 `show` 로 부모와 자식을 따로 읽는다 |
- **위임 대상 스킬이 빠졌으면** — 그 판단을 대신할 스킬을 4단계에서 조사한다. 없는 스킬을 부르라는 지시가 생성물에 남는 것이 최악이다.

결과를 사용자에게 요약하고, 조건부 항목을 지금 설치할지 아니면 그 단계를 빼고 갈지 확인한다.

# 1. 워크플로우를 수집한다

사용자의 설명을 받고, 저장소를 관찰해 보강한다. 설명만으로는 항상 부족하다 — 매일 하는 일일수록 말로 안 나온다.

관찰할 것: 언어·테스트 러너·CI 설정·배포 스크립트·기존 자동화·최근 커밋 패턴·`CLAUDE.md`.

수집한 것을 **단계 목록 초안**으로 제출하고 확인받는다. 여기서 빠진 단계는 끝까지 빠진다.

# 2. 이음매와 위임을 가른다

모든 단계를 스킬로 만들지 않는다. 기존 스킬을 감싸기만 하는 스킬은 지시문을 한 겹 늘리고 원본의 품질을 희석한다.

판정 기준은 `references/stage-patterns.md`에 있다. 요약하면 **도구 사이를 잇거나 프로젝트 고유의 결정이 담기면 이음매(스킬로 만듦), 일반적인 판단이면 위임**이다.

# 3. 증거를 어디에 남길지 정한다

검증 hook 이 무엇을 기준으로 문서를 찾을지가 여기서 정해진다. 정하지 않으면 검증이 비결정적이 된다. 반드시 묻는다.

```
증거를 어디에 남기나?
  (a) beads 티켓 필드 — 파일이 안 늘고 티켓이 SSoT
  (b) 폴더 — 루트 경로 아래 티켓 ID로 하위 폴더
  (c) 그 외 — 절차를 서술
```

스크린샷·영상처럼 파일이 필요한 증거가 있으면 (a)로는 부족하다.

**검사가 걸린 단계의 산출물은 파일이다.** 인용·부정·커버리지 검사와 프로젝트 불변식은 hook 이 문서를 읽어서 판정하므로, 그 검사를 걸 단계는 (a)를 골랐더라도 산출물을 파일로 남기고 스펙에 `artifact`(문서 종류와 폴더)를 단다. hook 은 문서를 경로가 아니라 frontmatter 의 `type`·`ticket` 두 줄로 찾는다 — 그 단계의 스킬 본문이 문서 머리에 이 두 줄을 쓰게 만든다. 규칙은 `references/evidence-patterns.md`.

# 4. 필요한 스킬을 조사하고 협의한다

**설치된 것부터 본다.** 있는데 모르고 새로 설치하는 게 가장 흔한 낭비다. 없으면 `find-skills` 스킬로 단계 키워드를 검색한다.

결과를 네 등급으로 분류한다.

| 등급 | 뜻 | 없을 때 |
|---|---|---|
| 필수 | 이 단계가 성립하지 않음 | 생성 중단하고 보고 |
| 추천 | 품질이 오르지만 단계는 돔 | 스펙에 "미설치"로 기록 |
| 대안 | 같은 일을 하는 후보가 복수 | 사용자가 고름 |
| 제외 | 이미 있는 것과 겹침 | 왜 제외했는지 기록 |

후보마다 설치 수·URL·분류 근거를 붙여 제시하고 사용자가 정한다. **자동으로 설치하지 않는다.**

검색에 나오지 않은 패키지명을 스펙에 쓰지 않는다. 있을 법한 이름을 지어내는 것이 이 단계의 실패 방식이다.

# 5. 정의 단계에는 축을 붙인다

"이 단계는 무언가를 정의·설계하는가"를 묻는다. 그렇다면 **무엇을 정의해야 하는지의 목록**이 없으면 완전성을 판정할 수 없다.

축 없이 통과시키면 검토된 축만 완벽하고 안 본 축은 존재조차 인지되지 않는다. 그 누락은 구현이 끝난 뒤 결과물에서 발견되어 재작업이 된다.

**먼저 축 저장소를 당긴다.** 같은 도메인을 이미 한 번 겪었다면 그때의 회고가 여기 쌓여 있다.

```bash
"${CLAUDE_PLUGIN_ROOT}/scripts/axis-sync.sh" pull
"${CLAUDE_PLUGIN_ROOT}/scripts/axis-sync.sh" list
```

매칭되는 도메인이 있으면 `resolve <도메인>`으로 꺼내(`extends`가 병합된 형태다) **출발점으로 제시한다.** 없으면 새 도메인이므로 아래 네 출처로 도출한다 — 저장소에 새 도메인으로 올릴지는 8단계에서 정한다(기본은 올리지 않는 것이다). 저장소가 아직 없으면(`pull`이 "does not exist"로 실패) 그 사실만 알리고 계속 간다 — 축 도출이 막히지는 않는다. 최초 1회는 `axis-sync.sh init`이 씨앗을 만든다.

저장소에서 꺼낸 축도 **그대로 쓰지 않는다.** 이 프로젝트에 해당하지 않는 축은 빼고, 왜 뺐는지 사용자에게 확인받는다. 남의 프로젝트 축을 다 켜면 "해당 없음" 행만 늘어난다. 뺀 축은 버리지 않고 스펙의 `axes_excluded` 에 이유와 함께 적는다 — 검사는 읽지 않지만, 나중에 그 축이 필요했다고 드러났을 때 retro 가 「몰랐다」와 「알고 뺐다」를 가를 근거다.

검사가 읽는 축의 정본은 저장소가 아니라 **프로젝트 스펙**이다. 저장소는 여기서 한 번 꺼내 쓰는 출발점이고, 그 뒤로 스펙과 저장소는 따로 자란다.

축은 네 출처로 도출한다 — 사용자 인터뷰, 저장소 관찰, **참조 구현 관찰**(마이그레이션이면 as-is가 정의하는 것이 곧 축 목록), 회고 축적. 저장소 구조와 조건부 적용(`when`) 문법은 `references/axis-patterns.md`에 있다.

축과 **충족 근거를 짝지어** 제시하고 컨펌받는 형태로 설계한다. 근거가 비는 축이 눈에 띄는 것이 이 방식의 값이다.

저장소의 축은 질문(`ask`)만이 아니라 **판정 기준**(`closed_when`·`excluded_when`)을 갖고 온다. 산출물 형태를 정할 때 그 기준이 행에 실제로 담기게 만든다 — 담기지 않으면 커버리지 검사가 빈칸을 잡을 뿐 기준 자체는 아무 데도 없게 된다.

산출물은 **첫 칸이 축 id 인 표**로 고정한다. 검사는 그 행만 인정하고, 스펙의 축에 더해 내장 축 `unlisted` 의 행 하나를 모든 문서에 요구한다. 표의 형태와 `unlisted` 의 정의는 `references/axis-patterns.md` 에 있다 — 정의 단계의 스킬 본문이 그 표를 쓰게 만든다. `unlisted` 는 스펙의 `axes` 에 넣지 않는다.

# 6. 구현 전 프리뷰를 넣을지 판단한다

정의 산출물을 실행 가능한 형태로 렌더링할 수 있으면 넣는다. 문서로만 있으면 빠진 절은 스크롤하며 넘어가지지만, 렌더링하면 빠진 정의가 눈에 보이는 결함이 된다.

넣는 조건: 산출물이 화면·문서·구조처럼 **볼 수 있는 것**이고, 최종 결과물이 나오기까지 오래 걸릴 때.

정직한 렌더링 규칙과 as-is 파일 대조 절차는 `references/preview-patterns.md`에 있다. 프리뷰가 그럴듯하게 나오면 실패라는 점이 핵심이다.

넣기로 했으면 스펙에서는 독립 단계가 아니라 정의 단계의 `preview` 키로 적는다. 그 파일이 없으면 티켓 닫기가 막힌다.

# 7. 단계마다 검증을 설계한다

검증 6종(존재·인용·실행·불변식·부정·커버리지)과 단계 성격별 선택표는 `references/evidence-patterns.md`에 있다.

세 가지를 정한다.

- **무엇을 거나** — 일률적으로 여섯을 다 걸면 대부분이 형식적 통과 의례가 된다. 그 단계가 실제로 취약한 지점에만 건다.
- **스킬 본문인가 hook인가** — 본문은 권고라 건너뛸 수 있고, hook은 harness가 실행하므로 못 건너뛴다. 인용·부정·커버리지·프리뷰 존재는 hook 이 맡는다. 존재·실행처럼 hook 이 읽지 않는 검사는 그 단계의 스킬 본문이 증거를 내게 한다.
- **프로젝트 고유 검사가 있는가** — 문서를 읽어 기계적으로 판정할 수 있는 규칙(합계가 맞는가, 필수 절이 있는가)은 스크립트로 만들어 그 단계의 `invariants` 에 단다. 닫기 직전에 돌고 실패하면 닫기를 막는다.

**시점과 차단 여부는 고르지 않는다.** 검사 종류가 정한다 — 인용(차단)·부정(경고)은 문서를 쓴 직후에, 커버리지·프리뷰 존재·불변식(차단)은 `bd close` 직전에 돈다. 차단하는 검사에는 대상 하나만 통과시키는 우회가 이미 들어 있다. 설계할 것은 **인용 규칙과 부정 패턴**이다: 이 프로젝트의 문서가 무엇을 인용하고(확장자·폴더) 어디서 찾아야 하는지, 「찾아봤는데 없었다」는 주장이 어떤 문구로 나오는지를 저장소의 실제 문서에서 관찰해 스펙의 `citations`·`negation` 에 적는다. 넓게 잡으면 오탐이 쏟아지고, 오탐이 쏟아지는 검사는 꺼진다.

생성되는 플러그인으로 복사할 것은 셋이다. **스크립트는 한 글자도 고치지 않는다** — 프로젝트마다 다른 것은 전부 스펙에 있고, 사본이 원본과 같아야 wf 가 올라갈 때 다시 복사할 수 있다.

| 원본 (이 플러그인 루트 기준) | 생성물에서의 자리 |
|---|---|
| `scripts/hook-post-edit.mjs`, `scripts/hook-pre-close.mjs` | 같은 경로 |
| `scripts/lib/` 의 `.mjs` 전부 | 같은 경로 |
| `templates/hooks.json` | `hooks/hooks.json` |

`lib/` 에서 하나라도 빠지면 hook 이 import 오류로 끝난다. hook 은 node 로 돈다.

# 8. 스펙에 기록한다

협의 결과를 프로젝트의 `.claude/<플러그인명>.spec.jsonc`에 쓴다. 파일 이름의 `<플러그인명>` 은 생성되는 플러그인의 `plugin.json` 의 `name` 과 같아야 한다 — hook 이 그 이름으로 스펙을 찾는다. 형식은 `${CLAUDE_PLUGIN_ROOT}/templates/workflow.spec.jsonc`, 소프트웨어 개발 기본형은 `spec-software-dev.spec.jsonc`. 주석(`//`, `/* */`)을 허용하는 JSON 이고 후행 쉼표는 안 된다. 스펙에 담기지 않는 사정은 옆의 `.claude/<플러그인명>.notes.md`(`templates/workflow.notes.md`)에 쓴다 — 스크립트는 그 파일을 읽지 않는다.

쓴 뒤 스펙 리더로 읽어 본다. 깨진 스펙은 hook 을 오류로 끝내므로 인계 전에 여기서 잡는다.

```bash
node --input-type=module -e 'import { loadSpec } from "${CLAUDE_PLUGIN_ROOT}/scripts/lib/spec-file.mjs"; loadSpec(process.argv[1]); console.log("spec ok")' .claude/<플러그인명>.spec.jsonc
```

스킬 본문이 아니라 데이터로 두는 이유는 **축과 규약이 재생성 없이 자라야** 하기 때문이다. 회고로 축이 하나 늘 때마다 플러그인을 다시 만들어야 한다면 아무도 안 늘린다.

## 5단계에서 새 도메인을 도출했다면

축 저장소에 매칭되는 도메인이 없어 새로 도출한 경우다. **기본은 올리지 않는 것이다** — 프로젝트마다 도메인 파일이 하나씩 생기면 `list`가 목록으로서 쓸모없어지고, 남의 프로젝트에서 영구히 "해당 없음"인 축만 늘어난다.

올리는 조건은 하나다: **같은 종류의 다른 프로젝트에서도 이 축들이 대부분 그대로 켜지겠는가.** 이 저장소의 특정 모듈·이 팀만의 규칙에 기댄 축이 절반을 넘으면 올리지 않고 프로젝트 스펙에만 둔다. 판단이 서지 않으면 사용자에게 묻는다.

올리기로 했으면 기존 도메인을 상속할 수 있는지부터 본다. `frontend`가 있는데 Vue 프로젝트라면 새 도메인이 아니라 `extends`다 — 공통 축을 베끼면 한쪽만 고쳐지고 갈라진다.

```bash
"${CLAUDE_PLUGIN_ROOT}/scripts/axis-sync.sh" pull
"${CLAUDE_PLUGIN_ROOT}/scripts/axis-sync.sh" list   # 상속할 부모가 있나
cat > "$("${CLAUDE_PLUGIN_ROOT}/scripts/axis-sync.sh" path)/axes/<도메인>.json" <<'JSON'
{ "schema": 1, "domain": "<도메인>", "description": "<어떤 작업에 켜지나>",
  "extends": ["<부모 도메인>"],
  "axes": [ { "id": "<영문-소문자>", "when": "", "ask": "...", "source_hint": "...",
              "closed_when": "<행이 무엇을 담고 있어야 이 축이 닫힌 것인가>",
              "excluded_when": "<무엇을 찾아본 뒤라야 「해당 없음」이라 쓸 수 있나>",
              "added_by": "<이 축이 어디서 나왔나 — 관찰이면 무엇을 관찰했는지>" } ] }
JSON
"${CLAUDE_PLUGIN_ROOT}/scripts/axis-sync.sh" ids <도메인>          # 병합 결과 확인
"${CLAUDE_PLUGIN_ROOT}/scripts/axis-sync.sh" push "add <도메인> domain"
```

`added_by`는 여기서도 비우지 않는다. 설계 단계의 축은 재작업이 아니라 관찰에서 나오므로 **무엇을 관찰했는지**를 쓴다 — "as-is의 `LegacyDetail.vue` 스타일 레이어가 별도로 존재", "기존 엔드포인트 12개 전부 멱등 키를 다룸" 같은 것. "일반적으로 필요"는 근거가 아니다.

형식과 운영 규칙은 `references/axis-patterns.md`에 있다.

# 9. create-plugin에 인계한다

스펙과 함께 넘긴다. create-plugin의 Phase 1~3(발견·컴포넌트 계획·상세 설계)은 이미 끝난 상태이므로 **Phase 4부터 시작하도록** 명시한다.

넘기는 것: 플러그인 이름, 만들 스킬 목록과 각각의 트리거 문구·본문 요지, 필요한 hooks와 그 스크립트, 복사할 references·templates·scripts, 스펙 파일 경로.

템플릿의 `<plugin>:`은 자리표시자다. 복사할 때 생성 플러그인 이름으로 바꾼다. `PRIME.md`의 스킬 목록에는 기본 스펙의 이음매 단계가 적혀 있을 뿐이므로 **이 스펙의 이음매 단계로 다시 쓴다** — `domain.md`와 `triage-labels.md`가 가리키는 `sources`·`slice`도 그 단계가 없으면 지운다. `PRIME.md`는 매 세션 주입되므로 여기 남은 한 줄은 없는 스킬을 부르라는 지시가 세션마다 반복되는 것이다.

```bash
grep -rn '<plugin>:' <생성된 플러그인과 복사된 문서 경로>    # 남아 있으면 치환이 빠진 것
```

생성되는 모든 스킬에 공통으로 박을 규칙도 함께 넘긴다.

> "확인했다", "동작한다", "통과한다"는 옆에 명령 출력이 없으면 근거가 아니다. 관찰한 것과 추론한 것을 문장에서 분리한다.

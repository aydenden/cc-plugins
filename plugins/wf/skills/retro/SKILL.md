워크플로우가 시간이 지나며 좋아지는 유일한 경로다. 놓친 것을 사람 기억에 맡기면 다음에도 놓친다. 스펙에 넣으면 다음 실행부터 자동으로 강제된다.

개선은 두 갈래로 나뉘고, 비용이 크게 다르다.

| 갈래 | 무엇을 고치나 | 생성물 수정 |
|---|---|---|
| **축 추가** | 스펙의 `axes` | 불필요 — 실행 시점에 읽힌다 |
| **구조 변경** | 스펙의 `stages`·`skills`·`evidence_store` | 필요 — 스킬 본문을 고쳐야 한다 |

먼저 축으로 해결되는지 본다. 축으로 되면 거기서 끝난다.

스펙은 프로젝트의 `.claude/<플러그인명>.spec.jsonc` 다 — 주석(`//`, `/* */`)을 허용하는 JSON 이고 후행 쉼표는 안 된다. 생성된 플러그인의 hook 이 실행 시점마다 이 파일을 읽는다.

이 플러그인의 루트는 `${CLAUDE_PLUGIN_ROOT}` 다. references 의 명령과 경로(`scripts/…`, `templates/…`)는 전부 이 루트 기준 상대 경로로 적혀 있으므로, 실행할 때 이 루트를 앞에 붙인다 — Bash 환경에는 이 변수가 없다.

축 문법과 도메인별 기본값은 `${CLAUDE_PLUGIN_ROOT}/references/axis-patterns.md`, 구조 변경 반영 절차는 `${CLAUDE_PLUGIN_ROOT}/references/spec-change.md`에 있다.

한 주기를 통째로 돌아보는 경우라면 사건을 먼저 나열하고 하나씩 아래를 돈다. 여러 건을 뭉쳐 한 번에 결론 내리면 원인이 뭉개진다.

# 1. 무엇이 빠졌는지 사실만 적는다

재작업의 내용이 아니라 **누락된 대상**을 특정한다. "스타일이 잘못됐다"가 아니라 "스타일이 정의된 적이 없다"가 이 단계의 산출물이다.

틀린 것과 없는 것은 다른 실패다. 틀린 것은 검증의 문제이고, 없는 것은 커버리지의 문제다. 이 스킬은 후자를 다룬다. 틀린 것이면 `/diagnosing-bugs`가 맞다.

# 2. 어느 단계에서 빠졌는지 찾는다

가장 이른 단계를 찾는다. 대개 정의·설계 단계다 — 그 이후 단계는 정의된 것을 성실히 수행했을 뿐이다.

각 단계의 산출물을 거슬러 올라가며 묻는다: **이 단계의 결과물에 그것이 있었어야 하나?** 있었어야 하는데 없는 가장 앞 지점이 원인 단계다.

구현 단계를 탓하지 않는다. 정의에 없는 것을 구현이 알아서 채우기를 기대하면 커버리지 문제가 영원히 안 고쳐진다.

# 3. 축으로 해결되는지 판단한다

그 단계에 무슨 항목이 있었으면 이번 누락이 드러났을지를 묻는다.

원인 단계의 산출물에서 **`unlisted` 행부터 읽는다**(정의는 `references/axis-patterns.md`). 이번에 빠진 것이 거기 「축 후보」나 후속 티켓으로 적혀 있었다면 몰랐던 것이 아니라 적어 놓고 따라가지 않은 것이고, 같은 종류의 항목이 여러 문서의 그 행에 되풀이됐다면 그것이 추가할 축이다. 스펙의 `axes_excluded` 도 본다 — design 이 알고 뺀 축이면 그때의 이유가 지금도 맞는지가 질문이다.

축은 **한 번의 사고에 하나만** 추가한다. 재작업 하나에서 축 다섯 개를 뽑으면 목록이 빠르게 형식화되고, 형식화된 목록은 안 보게 된다.

이미 있는 축인데 안 지켜진 것이라면 축을 늘리지 않는다. 그건 강제가 약한 것이므로 **검사를 hook으로 올리거나 산출물 형태를 고쳐야** 한다 — 구조 변경이다. 축 추가로 해결하려 들면 목록만 길어지고 같은 일이 반복된다.

안 지켜졌는지는 우회 로그가 말해준다. 그 축이 몇 번 우회됐는지 먼저 본다 — 위치와 형식은 `${CLAUDE_PLUGIN_ROOT}/references/evidence-patterns.md`.

```bash
grep -F "<축 id>" "${WF_BYPASS_LOG:-$(git rev-parse --git-common-dir)/wf-bypass.log}"
```

같은 축이 반복해서 우회됐다면 축을 더할 일이 아니다. 먼저 검사가 오탐을 낸 것인지 본다 — 우회가 존재하는 이유가 오탐이므로 가장 먼저 의심할 원인이다. 오탐이면 스크립트를 별도 변경으로 고친다. 오탐이 아니면 그 축이나 산출물 형태를 고친다.

# 4. 축을 스펙에 추가한다

`.claude/<플러그인명>.spec.jsonc`의 `axes` 에서 그 단계의 키(단계의 `"axes"` 값) 아래 배열에 넣는다. `axes_excluded` 에 있던 축을 되살리는 것이면 거기서 지운다.

```jsonc
{
  "id": "style",
  "when": "화면에 렌더링되는가",
  "ask": "시각 정의의 출처는 — 목업? 디자인 토큰? 기존 컴포넌트 재사용?",
  "source_hint": "정적 목업, 디자인 파일 프레임, as-is 구현의 스타일 레이어",
  "closed_when": "치수·색·타이포·radius·간격이 **값마다 출처와 함께** 적혀 있다",
  "excluded_when": "정본에 이 화면이 없다는 것을 찾아본 뒤 적는다 — 어디를 봤는지와 확인 시점이 함께 들어간다",
  "added_by": "<언제 어떤 재작업 때문에 추가됐는지>"
}
```

추가한 다음 닫는 티켓부터 그 축의 행이 없는 문서는 닫기가 막힌다. 진행 중인 문서도 예외가 아니므로, 열려 있는 정의 문서가 있으면 그 사실을 보고에 넣는다. `unlisted` 는 검사가 스스로 묻는 축이라 여기 넣지 않는다 — 넣으면 스펙 리더가 오류를 내고 hook 이 오류로 끝난다.

**판정 기준 둘을 이번 사고에서 뽑는다.** 이번에 무엇이 있었으면 잡혔을지가 곧 `closed_when`이고, 무엇을 찾아봤어야 「해당 없음」이라 말할 수 있었는지가 `excluded_when`이다. 사고 직후가 이 둘을 쓸 수 있는 유일한 시점이다 — 나중에 쓰면 일반론이 되고, 일반론은 아무 행도 막지 못한다.

`added_by`를 비우지 않는다. 목록이 길어졌을 때 실제 사고에서 나온 축과 그냥 넣어본 축이 구분되지 않으면 전체가 통과 의례가 된다. 나중에 목록을 정리할 때 이 필드가 유일한 판단 근거다.

`when`을 붙일지 정한다. 모든 작업에 해당하면 비우고, 조건부면 조건을 쓴다. 검사는 `when` 을 평가하지 않는다 — 조건이 거짓인 작업에서도 그 축의 「해당 없음 — 사유」 행은 요구된다. `when` 은 그 행을 쓰는 사람이 무엇을 기준으로 켜고 끄는지 읽는 자리다.

## 도메인 일반이면 저장소에도 올린다

이 축이 **같은 종류의 다른 프로젝트에서도 같은 누락을 잡았을 것인가**를 묻는다. 그렇다면 프로젝트 스펙에만 두면 다음 프로젝트에서 같은 재작업을 다시 겪는다.

**스펙에서 저장소로 복사한다 — 옮기지 않는다.** 검사가 읽는 것은 프로젝트 스펙이고 저장소는 `wf:design` 의 출발점일 뿐이라, 저장소에만 올리면 이 프로젝트에서는 아무것도 강제되지 않는다. 도메인은 스펙의 `domain` 값이다(`null` 이면 출발점 도메인이 없던 것이므로 어느 도메인에 넣을지 사용자와 정한다).

```bash
"${CLAUDE_PLUGIN_ROOT}/scripts/axis-sync.sh" pull
"${CLAUDE_PLUGIN_ROOT}/scripts/axis-sync.sh" retired <도메인>   # 전에 뺀 축인가부터 본다
# $(axis-sync.sh path)/axes/<도메인>.json 의 axes 배열에 스펙의 그 항목을 복사 (added_by 그대로)
"${CLAUDE_PLUGIN_ROOT}/scripts/axis-sync.sh" push "add <axis-id> to <도메인>"
```

저장소 파일은 순수 JSON 이다. 스펙에서 가져올 때 주석을 떼고 온다.

**`retired`를 먼저 본다.** 한 번 빼기로 결정한 축이 몇 달 뒤 그럴듯해 보여 다시 들어오는 것이 이 목록이 망가지는 흔한 경로다. 거기 있는 축이면 다시 넣기 전에 `retired_by`의 판단이 왜 뒤집혔는지를 먼저 말할 수 있어야 한다.

반대로 축을 **뺄 때는 지우지 않고 `retired`로 옮기고 이유를 적는다.** 지우면 근거가 히스토리에만 남고, 아무도 히스토리를 grep하지 않는다.

프로젝트 고유의 축 — 이 저장소의 특정 모듈, 이 팀의 특정 규칙 — 은 올리지 않는다. 올리면 다른 프로젝트에서 영구히 "해당 없음"인 행이 된다. 판단이 서지 않으면 사용자에게 묻는다.

`added_by`는 저장소로 옮길 때도 **원래 사건을 그대로 유지한다.** 축이 어느 재작업에서 나왔는지가 나중에 목록을 정리할 때 유일한 판단 근거다.

# 5. 더 이른 검사가 가능했는지 본다

축 추가는 다음번을 위한 것이지 발견 시점을 당기지 못한다. **이번에 왜 늦게 발견됐는지**를 함께 본다.

- 결과물을 보고서야 알았다면 → 구현 전 프리뷰 단계가 있었으면 잡혔을까? (`references/preview-patterns.md`)
- 참조 구현이 있었다면 → as-is 파일 목록과 정의 항목을 대조했으면 잡혔을까?
- 근거 표에 빈칸으로 떴어야 했다면 → 축과 충족 근거를 짝지어 제시하는 형태였나?

여기서 나온 것은 축이 아니라 **구조 변경**이다.

# 6. 구조 변경이면 스펙을 고치고 반영한다

3단계나 5단계에서 구조 변경이 필요하다고 나왔을 때만 이 절을 탄다.

먼저 `${CLAUDE_PLUGIN_ROOT}/references/spec-change.md`를 읽는다. 변경 종류별 파급, drift 확인, 손수정 판별, 검증 절차가 거기 있다.

순서는 고정이다.

1. **drift 확인** — 스펙과 생성물이 이미 어긋나 있는지. 어긋나 있으면 어느 쪽이 옳은지 사용자에게 먼저 묻는다
2. **스펙 수정** — `.claude/<플러그인명>.spec.jsonc`
3. **영향 파일 산출** — 새로 만들 것, 고칠 것, 손수정이 감지된 것을 표로
4. **컨펌** — 승인 없이 파일을 건드리지 않는다
5. **반영** — `create-plugin`을 다시 부르지 않는다. 그것은 처음부터 만드는 도구라 손수정을 덮는다. 영향받는 파일만 편집한다
6. **검증** — frontmatter, `${CLAUDE_PLUGIN_ROOT}` 참조 실존, 제거된 스킬을 가리키는 잔여 문구, hooks.json 유효성, 스펙이 스펙 리더로 읽히는지

가장 자주 빠뜨리는 것은 **앞뒤 단계의 연결 문구**다. 단계를 하나 넣으면 앞 단계의 "다음은 X"와 뒤 단계의 "앞서 Y가 끝났으면"이 둘 다 어긋난다.

# 7. 보고한다

추가한 축과 계기, 고친 파일, 다음 실행부터 무엇이 달라지는지를 정리한다. 스펙 파일 경로를 함께 남긴다.

스펙과 생성물은 같은 커밋에 담길 때 추적이 유지된다. 커밋 명령을 제안하되 실행은 사용자 승인 후에 한다.

# 증거 검증 6종

생성되는 워크플로우의 각 단계는 "했다"고 말하는 대신 증거를 낸다. 다음 단계는 증거 없이 시작하지 않는다.

여섯 종류가 있고, 앞의 다섯은 **만들어진 것을 검사**하며 마지막 하나만 **만들어지지 않은 것**을 잡는다. 스펙의 `stages[].checks` 에는 오른쪽 이름으로 적는다 — 그 밖의 이름은 스펙 리더가 거부한다(오타가 검사를 조용히 끄지 않게).

| 종류 | 막는 실패 | 판정 방법 | `checks` 이름 |
|---|---|---|---|
| 존재 | 만들었다는데 없음 | 산출물 경로·ID를 실제로 열어본다 | `existence` |
| 인용 | 없는 파일·문서를 근거로 듦 | 인용한 경로가 실재하는가 | `citation` |
| 실행 | 안 돌리고 통과했다고 함 | exit code + 출력 캡처 경로 | `execution` |
| 불변식 | 상태가 기대와 다름 | 관계·개수·순환을 질의 | `invariant` |
| 부정 | 안 찾아보고 "없다"고 함 | 그 주장 근처에 검색의 흔적이 있는가 | `negation` |
| **커버리지** | **검토 축이 통째로 빠짐** | **스펙의 축마다 산출물 표에 행이 있는가** | `coverage` |

## 어느 단계에 무엇을 거나

일률적으로 여섯을 다 걸면 대부분이 형식적 통과 의례가 된다. 단계가 실제로 취약한 지점에만 건다.

| 단계 성격 | 걸어야 하는 것 |
|---|---|
| 조사·수집 | 인용, 부정 |
| 정의·설계 | **커버리지**, 인용 |
| 분해·적재 | 존재, 불변식 |
| 구현 | 실행 |
| 검증·테스트 | 실행, 존재 |
| 마감 | 실행, 불변식 |

인용과 부정은 특히 중요하다. 나머지는 안 하면 다음 단계에서 티가 나지만, **없는 근거를 지어내는 것과 안 찾아보고 없다고 하는 것은 끝까지 티가 안 난 채 흘러간다.**

## 스킬 본문이 아니라 hook으로 건다

스킬 본문의 "증거를 내라"는 권고이고 건너뛸 수 있다. hook은 harness가 실행하므로 건너뛸 수 없다.

hook 은 둘이고, **무엇이 언제 도는지와 차단인지 경고인지는 스펙이 아니라 검사 종류가 정한다.** 스펙에는 그것을 고르는 키가 없다.

| 시점 | hook | 도는 검사 | 결과 |
|---|---|---|---|
| 문서를 쓴 직후 | `PostToolUse` (`Write\|Edit`) → `scripts/hook-post-edit.mjs` | 인용 | 차단 |
| | | 부정 | 경고 |
| | | frontmatter 선언 유무 (새 문서) | 경고 |
| `bd close` 직전 | `PreToolUse` (`Bash`) → `scripts/hook-pre-close.mjs` | 커버리지 | 차단 |
| | | 프리뷰 존재 (`preview` 를 단 단계) | 차단 |
| | | 프로젝트 불변식 (`invariants` 를 단 단계) | 차단 |

- **차단의 뜻은 시점마다 다르다.** 닫기 직전의 차단은 `bd close` 명령이 실행되지 않는 것이다. 편집 직후의 차단은 **쓰기를 되돌리지 못한다** — 파일은 이미 쓰였고, exit 2 의 stderr 가 모델에게 되돌아가 고치게 만든다.
- **인용이 편집 시점인 이유** — 경로가 없으면 그 근거는 존재하지 않는다. 쓴 자리에서 알려야 그 위에 다음 문장이 쌓이지 않는다. 닫기 게이트는 인용을 다시 돌리지 않는다.
- **커버리지가 닫기 시점인 이유** — 표는 여러 번의 편집으로 채워진다. 편집마다 돌리면 채우는 도중 내내 실패가 뜨고, 닫기가 실제로 막혀야 「차단」이 성립한다.
- **부정이 경고인 이유** — 검색 흔적의 누락은 대개 게으름이지 오류가 아니다. 경고는 `additionalContext` 로 모델에게 전달되고 아무것도 막지 않는다.
- **「프로젝트 루트」** 는 환경변수 `CLAUDE_PROJECT_DIR` 이고, 없으면 hook payload 의 `cwd` 다. git 루트를 따로 찾지 않는다. 스펙·마커·문서 경로가 전부 이 폴더 기준이다.

`checks` 에 적은 `existence`·`execution`·`invariant` 는 hook 이 읽지 않는다. 그 단계의 스킬 본문이 그 증거를 낸다는 선언이다. hook 으로 강제할 프로젝트 고유 검사는 아래 `invariants` 에 명령으로 단다.

### 검사는 산출물을 frontmatter 로 찾는다

문서를 읽는 검사(`coverage`·`citation`·`negation`)나 `invariants`·`preview` 를 건 단계는 스펙에 `artifact` 가 있어야 한다 — 없으면 스펙 리더가 오류를 낸다. **검사가 걸린 단계의 산출물은 파일이다.** 티켓 필드에만 남긴 산출물은 hook 이 읽을 수 없다.

```jsonc
"artifact": { "type": "definition", "dirs": ["docs/issues"] }
```

```markdown
---
type: definition
ticket: proj-142
---
```

- `dirs` 는 편집 hook 이 감시하는 범위다. 그 아래(하위 폴더 포함)의 `.md` 만 본다. `type` 은 단계마다 달라야 한다
- 닫기 게이트는 `dirs` 아래에서 `type` 이 그 단계의 값이고 `ticket` 이 닫으려는 ID 인 문서를 찾는다. 경로에 티켓 ID 가 없어도 된다
- frontmatter 에서 읽는 것은 이 두 `키: 값` 줄뿐이다
- **선언이 없는 문서는 닫기 게이트에 보이지 않는다.** 그래서 감시 범위에 문서를 `Write` 로 쓸 때 선언이 빠져 있으면 경고한다(`Edit` 에는 경고하지 않는다 — 조각만 보고는 새 문서인지 알 수 없다). 편집 검사는 선언이 없어도 돈다 — 그 폴더를 감시하는 모든 단계의 검사를 받는다
- 어느 문서도 선언하지 않은 티켓은 통과한다. 모든 티켓이 문서를 내지는 않는다
- 닫기로 읽는 것은 `bd close <id>...`·`bd done <id>...` 의 위치 인자와, 상태를 `closed` 로 바꾸는 `bd update <id>... --status closed` 다. `cd x && …` 뒤나 `NAME=value` 뒤에 있어도 읽는다. `--reason` 안의 글자와 따옴표 안의 `bd close` 는 읽지 않는다
- **읽지 못하는 닫기가 있다.** 스크립트 파일 안이나 `eval`·`xargs` 로 조립된 닫기는 명령 줄에 `bd close` 로 나타나지 않아 게이트를 지난다. 게이트는 실수로 닫는 것을 막는 장치이지 닫으려고 드는 것을 막는 장치가 아니다

### 스펙을 못 읽으면

스펙 파일(`.claude/<플러그인>.spec.jsonc`)이 없는 프로젝트에서는 두 hook 이 아무것도 하지 않고 통과한다. 스펙이 **깨져 있으면** exit 2 로 어디가 틀렸는지를 낸다 — 읽을 수 없는 스펙을 조용히 넘기면 모든 검사가 꺼진 것과 같기 때문이다. 닫기 hook 은 그 상태에서 티켓을 닫는 명령을 전부 막고(닫지 않는 `bd` 명령은 막지 않는다), 편집 hook 은 프로젝트의 `.md` 문서(감시 범위 밖이어도)나 스펙 파일 자체를 쓸 때마다 알린다 — 스펙을 읽지 못하면 감시 범위가 어디인지도 알 수 없다. 스펙을 고치면 풀린다.

## 인용 — 무엇을 인용으로 보고 어디서 찾나

규칙은 스펙의 `citations` 가 준다. 프로젝트마다 문서가 가리키는 것이 달라서, 고정된 규칙은 오탐만 낸다 — 저장소 루트 기준으로만 찾고 백틱 토큰을 전부 경로로 읽던 검사는 한 생성물에서 81건 전부가 오탐이었다.

- **인용으로 보는 것** — 백틱 토큰 중 `file_extensions` 로 끝나거나 `path_roots` 로 시작하는 것. 그 밖의 토큰(API 식별자, 도메인, 패키지 이름)은 인용이 아니다. 뒤에 붙은 `:줄` 과 `#앵커` 는 떼고 본다. URL 과 `~` 로 시작하는 경로는 건너뛴다. 공백이나 자리표시자·글롭·셸 문자(`<>`, `*`, `…`, `{}`, `$`, `=`, `()`, `|`, `,`, `[]`)가 든 토큰도 경로가 아니라고 보고 건너뛴다 — `docs/<ticket>/index.html` 이나 `src/**/*.ts` 는 검사되지 않는다
- **보는 범위** — 편집할 때마다 **문서 전체**의 인용을 본다. 이번에 고친 줄만이 아니다. 전에 쓴 인용이 가리키던 파일이 지워졌으면 다음 편집에서 걸린다
- **찾는 순서** — 저장소 루트 → 인용한 문서의 폴더 → `search_roots` → `index_roots` 안에서 경로 끝이 일치하는 파일. 어디서도 못 찾으면 `MISSING`
- **파일이 아닌데 걸리는 토큰** — `ignore_patterns` 에 정규식과 이유를 적는다
- `citation` 을 건 단계가 있으면 `file_extensions` 나 `path_roots` 중 하나는 있어야 한다

## 부정 — 무엇을 주장으로 보나

규칙은 스펙의 `negation` 이 준다. 기본값은 없다 — 「없다」「없음」 같은 넓은 패턴은 한국어 산문 어디에나 걸린다(한 생성물에서 223건). `claim` 은 **찾아봤는데 없었다**는 주장만 잡도록 좁히고, `proof` 는 그 근처에 있어야 하는 검색의 흔적이다.

- 이번 편집이 쓴 줄만 본다. 전에 쓰인 줄은 다시 경고하지 않는다
- `claim` 에 맞는 줄과 그 위아래 6줄 안에 `proof` 에 맞는 줄이 없으면 `UNPROVEN`. 주장한 줄 자신도 포함이다 — 「`rg` 로 찾지 못했다」처럼 한 줄에 둘이 있으면 통과한다
- 경고 전용이다. 막지 않으므로 우회도 없다

## 프리뷰와 불변식

```jsonc
"preview": "docs/previews/<ticket>/index.html",
"invariants": [{ "name": "ledger-sums", "run": ["node", "scripts/check-ledger.mjs"] }]
```

- `preview` 의 `<ticket>` 은 닫으려는 ID 로 바뀐다. 그 파일이 없으면 닫기를 막는다
- `invariants[].run` 은 인자 배열이다. **플러그인 루트를 작업 폴더로** 돌고, 문서의 절대 경로가 마지막 인자로 붙고, 프로젝트 루트는 환경변수 `CLAUDE_PROJECT_DIR` 로 온다. 0 이 아닌 종료 코드는 닫기를 막고 그 출력이 보고된다

## 우회에는 이유가 붙는다

우회 규칙의 정본은 이 절이다. 다른 문서는 여기를 가리킨다.

hook 은 오탐이 나면 작업을 막는다. **명시적 우회 경로를 반드시 둔다.** 우회할 수 없는 검사는 결국 꺼진다.

```bash
echo "style: 목업 미수령, proj-142" >> .claude/wf-skip-checks    # <대상>: <왜>, <티켓>
```

- **우회는 대상 단위다.** 마커의 한 줄은 그 줄이 이름 붙인 대상 하나만 통과시킨다. 대상은 실패 보고에 찍힌 그대로 적는다.

  | 검사 | 대상 | 로그의 검사 이름 |
  |---|---|---|
  | 커버리지 | 축 id (`unlisted` 포함) | `check-coverage` |
  | 인용 | 인용 경로 | `check-citations` |
  | 프리뷰 | 프리뷰 경로 | `check-preview` |
  | 불변식 | 불변식의 `name` | `check-invariant` |

  `style` 한 줄이 `state` 의 `UNADDRESSED` 나 인용 검사까지 끄지 않는다. 대상과 이유는 「콜론 + 공백」으로 가른다 — 인용 경로에 콜론이 들어갈 수 있다.
- **판정에 쓰이는 것은 대상뿐이다.** 줄 끝의 `<티켓>` 은 기록용이고 범위를 좁히지 않는다 — `style: …, proj-142` 가 마커에 있는 동안에는 **어느 티켓의 문서든** `style` 이 통과한다. 그래서 끝나면 줄을 지운다. 이유 칸의 형식도 검사하지 않는다(비어 있지만 않으면 된다).
- **안 맞는 줄은 아무것도 우회하지 않고, 그 사실을 알린다.** 형식이 틀린 줄, 지금 실패하고 있지 않은 대상을 적은 줄이 그렇다.
- **이유 없는 마커는 우회가 아니다.** 빈 파일이면 검사가 그대로 돌고, 무엇을 적어야 하는지 알려준다. 검사가 꺼지는 지점이 아무것도 남기지 않으면 "통과했다"와 "껐다"가 같은 출력이 되고, 아래 「자기 보고 금지」가 바로 거기서 뚫린다.
- **기록은 스크립트가 한다.** 우회가 성립하면 그 줄을 알리고(남은 실패가 있으면 실패 보고와 함께, 우회만으로 통과했으면 `additionalContext` 로) 로그에 `<날짜> <검사 이름>: <마커 줄>` 한 줄을 남긴다. 같은 날 같은 줄은 한 번만 남는다 — hook 은 편집마다 돌지만 우회는 한 번의 결정이다. 사람이 옮겨 적게 두면 마커를 지울 때 이유도 같이 사라진다. **기록하지 못하면 우회하지 않는다.**
- **로그는 워킹트리 밖에 산다.** `<git common dir>/wf-bypass.log` (`WF_BYPASS_LOG`로 변경, git 저장소 밖이면 `.claude/wf-bypass.log`). 프로젝트 폴더에 두면 커밋할 수 없는 저장소에서는 남길 곳이 없고, 워크트리는 작업이 끝나면 지워진다. git common dir는 모든 워크트리가 공유하고 커밋 대상이 아니다. 대신 clone을 넘어가지 않는다.
- **마커 줄은 끝나면 지운다.** 마커는 "지금 우회 중"이라는 상태이고, 이력은 로그다.

같은 대상이 반복해서 우회되면 그 검사나 축, 또는 산출물 형태가 틀렸다는 신호다. `wf:retro`가 이 로그를 읽는다.

## 자기 보고 금지

생성되는 모든 스킬에 공통으로 박는다.

> "확인했다", "동작한다", "통과한다"는 옆에 명령 출력이 없으면 근거가 아니다. 관찰한 것과 추론한 것을 문장에서 분리한다.

## 스크립트

검사는 node 만 요구한다(`node:` 내장 모듈만 쓴다). 경로는 wf 플러그인 루트 기준이다.

| 파일 | 하는 일 |
|---|---|
| `scripts/hook-post-edit.mjs` | 편집 직후 hook 의 진입점 |
| `scripts/hook-pre-close.mjs` | 닫기 직전 hook 의 진입점 |
| `scripts/lib/hooks.mjs` | 두 hook 의 본체 — 스펙·파일·프로세스를 잇는다 |
| `scripts/lib/edit-gate.mjs` · `close-gate.mjs` | 시점별 판정 |
| `scripts/lib/spec.mjs` · `spec-file.mjs` | 스펙 리더 |
| `scripts/lib/artifact.mjs` | 감시 범위와 frontmatter 선언 |
| `scripts/lib/coverage.mjs` | 커버리지 판정 (규칙의 주인은 `axis-patterns.md`) |
| `scripts/lib/citations.mjs` · `citations-file.mjs` | 인용 판정과 파일 조회 |
| `scripts/lib/negation.mjs` | 부정 판정 |
| `scripts/lib/bypass.mjs` · `bypass-file.mjs` | 우회 판정과 기록 |
| `templates/hooks.json` | 두 hook 을 거는 설정 |

생성기는 `scripts/hook-post-edit.mjs`·`scripts/hook-pre-close.mjs` 와 `scripts/lib/` 의 `.mjs` 전부를 생성되는 플러그인의 같은 경로로 **고치지 않고** 복사하고, `templates/hooks.json` 을 `hooks/hooks.json` 으로 둔다. 프로젝트마다 다른 것은 전부 스펙의 데이터라서 사본은 원본과 바이트 단위로 같게 유지된다 — 스크립트는 스펙 경로를 자기 플러그인의 `plugin.json` 의 `name` 으로 구하므로(`.claude/<name>.spec.jsonc`) 이름을 박을 곳이 없다. `scripts/test/` 는 복사하지 않는다. 사본이 원본과 같은지는 `spec-change.md` 의 drift 확인이 본다.

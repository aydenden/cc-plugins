# 정의 프리뷰 — 구현 전에 누락을 보이게 만들기

정의가 문서로만 있으면 빠진 절은 스크롤하며 넘어가진다. 렌더링하면 빠진 정의가 **눈에 보이는 결함**이 된다. 정의를 컴파일해서 실행해 보는 것이다.

구현이 끝난 뒤 결과물을 보고 누락을 발견하면 재작업이다. 프리뷰는 그 발견 시점을 구현 **전**으로 당긴다.

## 규칙 1 — 정직하게 렌더링한다

프리뷰가 그럴듯하게 나오면 실패한다. 정의되지 않은 스타일을 알아서 채우면 구멍이 메워져 원래 문제로 돌아간다.

**정의된 것만 렌더링하고 미정의는 미정의로 표시한다.**

```
[ 상품 상세 영역 ]        ← behavior 정의됨
┌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌┐
┆ 스타일 미정의     ┆     ← 회색 해치 + 라벨. 채우지 않는다
└╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌┘
[ 로딩 상태 ] 미정의
[ 빈 상태 ] 정의됨: "등록된 상품이 없습니다"
[ 에러 상태 ] 미정의
```

목적은 예쁜 결과물이 아니라 **구멍의 가시화**다. 뒤집으면 도구가 무용해진다.

## 규칙 2 — 버리는 산출물이다

정적 HTML 한 장. 프레임워크 없음, 빌드 없음, 배포 없음. 구현에 재사용하려 들면 프리뷰가 무거워지고, 무거워지면 만들지 않게 된다.

기존 `/prototype` 스킬과 목적이 다르다. prototype은 설계 질문에 답하려 코드를 쓰고, 프리뷰는 **정의의 완전성**을 드러낸다. 렌더링 기법은 빌려도 되지만 판단 기준은 다르다.

## 규칙 3 — as-is와 대조한다

as-is 촬영본이 있으면 자동 신호를 얻는다.

```bash
agent-browser open "file://$(pwd)/preview.html"
agent-browser screenshot preview.png --full
agent-browser diff screenshot --baseline <as-is 촬영본>
```

스타일이 미정의면 diff가 크게 뜬다. 사람이 눈으로 보기 전에 신호가 먼저 온다.

## 프리뷰로 잡히지 않는 축

| 축 | 프리뷰 |
|---|---|
| 스타일 · 레이아웃 · 상태 · 반응형 | 잡힌다 |
| 성능 · 보안 · 코드 중복 · 반복 이슈 | 잡히지 않는다 |

프리뷰 하나로 커버리지 검사를 대체할 수 없다. 렌더링되지 않는 축은 다른 방법이 필요하다.

## 짝이 되는 검사 — as-is 파일 대조

프리뷰보다 싸고, 프리뷰가 못 잡는 레이어(테스트·유틸)까지 잡는다.

```
as-is:  LegacyDetail.vue · detail.scss · useDetailData.ts · detail.spec.ts
to-be:  behavior ✓   data ✓   test ✓   style ✗   ← 미매칭
```

원본에 있는 레이어인데 to-be 정의에 대응물이 없으면 그 자리에서 뜬다. 마이그레이션 워크플로우에는 반드시 넣는다.

**둘을 같이 건다.** 파일 대조가 구조적 누락을, 프리뷰가 시각적 누락을 잡는다.

## 단계 배치

```
정의(축 + 근거) → as-is 대조 + 정적 프리뷰 → 사용자 컨펌 → 구현
                   └─ 여기서 발견. 구현 전
```

프리뷰 단계의 통과 조건은 "예쁘다"가 아니라 **"미정의 표시가 모두 의도된 것인가"**다. 의도치 않은 미정의가 하나라도 있으면 정의 단계로 돌아간다.

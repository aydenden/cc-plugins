# 축 — 정의 단계의 커버리지

정의·설계 단계는 **무엇을 정의해야 하는지의 목록**이 있어야 완전성을 판정할 수 있다. 그 목록의 항목을 축이라 부른다.

축 없이 정의 단계를 통과시키면 검토된 축만 완벽하고 안 본 축은 존재조차 인지되지 않는다. 그 누락은 구현이 끝난 뒤 결과물에서 발견되어 재작업이 된다.

## 축은 조건부로 켜진다

기능 성격에 따라 적용 축이 달라진다. 안 켜진 축은 사라지는 게 아니라 **"해당 없음"으로 명시**된다. 판단한 적 없는 것과 판단해서 뺀 것은 다르다.

`when` 은 사람이 읽는 조건이다. **검사는 `when` 을 평가하지 않는다** — 스펙에 있는 모든 축에 행을 요구하고, 안 켜진 축은 「해당 없음 — 사유」 행으로 남는다.

씨앗 `templates/axis-store/frontend.axes.json` 의 `style` 축이다.

```jsonc
{
  "id": "style",
  "when": "화면에 렌더링되는가",
  "ask": "시각 정의의 출처는 — 목업? 디자인 토큰? 기존 컴포넌트 재사용?",
  "source_hint": "정적 목업, 디자인 파일 프레임, as-is 구현의 스타일 레이어",
  "closed_when": "치수·색·타이포·radius·간격이 **값마다 출처와 함께** 적혀 있다",
  "excluded_when": "정본에 이 화면이 없다는 것을 찾아본 뒤 적는다 — 어디를 봤는지와 확인 시점이 함께 들어간다",
  "added_by": "2026-08 신규 화면 재작업 — 동작 13갈래를 정본 세 곳과 대조해 전부 확정했으나 시각 정합은 원장 어디에도 없었다. 목업을 5일 내내 갖고 있었지만 '무엇을 만드는가'로만 읽었고, 실측은 사용자가 지적하고서야 이뤄졌다"
}
```

`added_by`를 비우지 않는다. 목록이 길어졌을 때 실제 사고에서 나온 축과 그냥 넣어본 축이 구분되지 않으면 전체가 형식적 통과 의례가 된다.

## 축과 근거를 짝지어 제시하고 컨펌받는다

축만 나열하면 "고려했다"가 쉽게 성립한다. **각 축이 무엇으로 충족되는지**를 함께 붙이면 빈 곳이 드러난다.

```
이 이슈에 필요한 축과 충족 근거:
  behavior  ← 지라 본문, 컨플루언스 <링크>
  style     ← Figma <프레임>, as-is 촬영 <경로>
  state     ← 근거 없음  ⚠
  performance ← 해당 없음 (기획서 2.1절: 단건 정적 조회, 목록·페이징 없음)
진행할까요?
```

"근거 없음"이 눈에 띄는 것이 이 방식의 값이다.

## 축에는 질문만이 아니라 판정 기준이 붙는다

`ask`만 가진 축은 물음표만 갖고 이동한다. **무엇이면 닫힌 것인가**가 축과 함께 오지 않으면 프로젝트마다 그 기준을 다시 세우고, 다시 세운 기준은 대개 더 낮다.

- `closed_when` — 산출물의 행이 무엇을 담고 있어야 이 축이 닫힌 것인가
- `excluded_when` — 「해당 없음」이라 쓰려면 **무엇을 찾아본 뒤**여야 하는가

**「해당 없음」은 관측이지 침묵이 아니다.** 성립: `해당 없음 — 목업 3종·디자인 파일·기획서 어디에도 이 화면의 실패 상태가 없다 (2026-08-26 확인)`. 불성립: `해당 없음 — 이번 범위 아님`, 빈칸, `추후`. 찾아보지 않고 낸 판정은 산출물에서 찾아보고 낸 판정과 구분되지 않는다 — 그래서 기준을 축마다 적어 두고 사람의 재량에 맡기지 않는다.

## 산출물 형태를 고정해 셀 수 있게 만든다

"고려하라"는 권고는 지켜지지 않는다. 스펙의 그 단계에 축이 N개면 산출물의 표에 N+1개 행이 있어야 한다 — 축마다 하나, 그리고 아래의 `unlisted` 하나. 제외도 행이다.

```markdown
| 축 | 정의 | 출처 |
|---|---|---|
| behavior | ... | 기획서 3.2절 |
| style | ... | 목업 `mockup/detail.html`, as-is `LegacyDetail.vue:40-120` |
| state | 로딩 스켈레톤, 빈 목록 문구 | 목업 없음 → 기존 컴포넌트 준용 |
| i18n | 해당 없음 — 로케일 파일과 번역 키가 저장소에 없다 | `rg -l locale src` 0건 (2026-08-26 확인) |
| unlisted | 인쇄용 레이아웃 — 위 축 어디에도 없다 → 후속 티켓 | `proj-142` |
```

이러면 커버리지 검사(`scripts/lib/coverage.mjs`)가 결정적으로 판정한다. 판정은 둘뿐이고 둘 다 차단이다.

| 판정 | 뜻 |
|---|---|
| `UNADDRESSED` | 그 축의 행이 없다 — 아무도 안 봤다 |
| `INCOMPLETE` | 행은 있는데 뒤 칸이 없거나 비었거나, 「해당 없음」에 사유가 없다 — 근거 없는 판정 |

검사는 `bd close` 직전에 돈다. 언제 무엇이 도는지와 우회는 `evidence-patterns.md` 가 소유한다.

스크립트가 검사하는 것은 구조뿐이다 — `closed_when`의 **내용**이 충족됐는지는 사람이 본다. 빈칸을 통과시키지 않는 것만으로도 "고려했다"가 성립하는 가장 흔한 경로가 막힌다.

# 축은 어디서 오나 — 네 출처

**1. 사용자 인터뷰.** 가장 먼저 묻지만 가장 불완전하다. 놓친 축은 정의상 사용자도 모른다.

**2. 저장소 관찰.** 이 코드베이스에서 기능 하나가 실제로 무엇들로 구성되는지 역추출한다. 기존 기능 하나를 골라 관련 파일을 전부 나열하면 축이 드러난다. 스타일이 별도 레이어로 존재하면 스타일 축이 있는 것이다.

**3. 참조 구현 관찰.** 마이그레이션이면 **as-is 코드가 이미 정의하고 있는 것이 곧 to-be가 정의해야 할 축의 목록**이다. 추측이 아니라 관찰이라 가장 강하다.

**4. 회고 축적.** 실제 엔진. 아래 참조.

# 회고 루프

```
재작업 발생 → 어느 단계에서 빠졌나 → 어떤 축이 있었으면 잡혔나
            → 스펙의 axes 에 추가 (added_by 포함) → 다음 실행부터 강제
```

축 목록이 스킬 본문이 아니라 `.claude/<플러그인>.spec.jsonc`에 데이터로 있으므로 **재생성 없이 자란다.** 검사가 읽는 축의 정본은 이 프로젝트 스펙이다 — 아래의 축 저장소는 `wf:design` 이 출발점으로 꺼내 쓰는 곳일 뿐, 검사 시점에는 읽히지 않는다. design 이 출발점에서 뺀 축은 스펙의 `axes_excluded` 에 이유와 함께 남는다(검사는 읽지 않고 retro 가 읽는다). 이것이 워크플로우가 시간이 지나며 좋아지는 유일한 경로다. `wf:retro`가 이 절차를 소유한다.

# 행은 표의 첫 칸으로 찾는다

검사가 인정하는 행은 **표의 행이고 첫 칸이 축 id 와 정확히 일치하는 것**뿐이다. 그래서 id 는 영문 소문자·숫자·하이픈으로 고정하고, 설명은 한국어로 쓰되 행의 첫 칸에는 id 를 그대로 쓴다.

```markdown
| performance | 목록 500건까지 실측, 가상화 불필요 | as-is 실측 |
```

- 첫 칸 양끝의 꾸밈 문자(`*`, 백틱, `_`)는 벗기고 비교한다. `**style**` 은 `style` 의 행이다
- 대소문자까지 일치해야 한다. `Style` 은 `style` 의 행이 아니다
- **표 밖의 언급과 다른 칸의 언급은 행이 아니다.** 제목(`## style`)이나 본문 문장으로 다룬 축은 `UNADDRESSED` 다. `state`·`scope` 같은 id 는 흔한 단어라, 본문에 한 번 쓰인 것으로 통과시키면 축 하나가 아무 판정 없이 닫힌다
- 첫 칸이 `state-lifetime` 인 행은 `state` 의 행이 아니다. 접두사가 겹치는 id 를 피할 필요가 없다
- 같은 id 의 행이 여럿이면 첫 행으로 판정한다
- 행은 `|` 로 시작해야 한다. 앞 파이프를 생략한 표(`style | … | … |`)는 행으로 읽지 않는다
- 코드 펜스 안의 표 행도 행으로 센다. 문서에 예시 표를 붙여 두면 그 행이 축을 닫을 수 있으니, 정의 문서에는 실제 표만 둔다
- 「해당 없음」의 사유는 같은 행의 **어느 칸에 있어도** 된다. `| i18n | 해당 없음 | 로케일 파일 0건 확인 |` 은 사유가 있는 행이다

# 내장 축 `unlisted`

이 정의의 주인은 이 절이다. 다른 문서는 여기를 가리킨다.

엄격한 대조는 **목록에 있는 것**의 바닥일 뿐이다. 목록 밖에 있는 것은 축이 없어서 물을 수도 없다. 그래서 검사는 스펙의 축에 더해 `unlisted` 행 하나를 모든 산출물에 요구한다.

- **묻는 것** — 이 작업이 닿는 것 중 위 축 어디에도 속하지 않는 것은 무엇인가
- **닫히는 조건** — 항목마다 그것이 무엇인지와 처리가 적혀 있다. 처리는 셋 중 하나다: 이 문서에서 정의 / 후속 티켓 ID / 축 후보
- **「해당 없음」** — 무엇과 대조했는지를 적은 뒤에만 쓴다. 판정은 다른 축과 같다(사유 없는 「해당 없음」은 `INCOMPLETE`)
- **자리** — 문서당 한 행, 표의 마지막에 둔다. 다른 축이 정해져야 「목록 밖」이 무엇인지 정해진다. 순서는 검사하지 않는다
- **스펙에는 쓰지 않는다** — 검사가 스스로 묻는다. 스펙의 `axes` 에 이 id 를 넣으면 스펙 리더가 오류를 낸다

여기 적힌 항목은 모델의 판단이지만 **기록으로 남는다.** 「축 후보」가 같은 종류로 되풀이되면 그것이 다음 축이다 — `wf:retro` 가 이 행을 읽는다.

# 도메인별 기본 축 — 원격 저장소

기본 축은 이 문서에 하드코딩되지 않는다. 문서에 박아두면 도메인이 늘 때마다 스킬을 고쳐야 하고, 회고로 나온 축이 다음 프로젝트에 전달되지 않는다.

축은 저장소의 **커스텀 ref `refs/wf/axes`** 에 도메인별 JSON으로 산다.

명령은 wf 플러그인 루트 기준이다(루트 경로는 부른 스킬이 알려 준다).

```bash
scripts/axis-sync.sh init              # 최초 1회 — 씨앗으로 store 생성 (push 는 안 함)
scripts/axis-sync.sh path              # 로컬 store 경로
scripts/axis-sync.sh pull              # 생성 또는 fast-forward
scripts/axis-sync.sh list              # 어떤 도메인이 있나
scripts/axis-sync.sh show frontend     # 저장된 그대로
scripts/axis-sync.sh resolve frontend  # extends 병합된 도메인
scripts/axis-sync.sh ids frontend      # 병합된 축 id만, 한 줄에 하나
scripts/axis-sync.sh retired frontend  # 뺀 축과 뺀 이유
scripts/axis-sync.sh push "메시지"       # 커밋·발행
```

**왜 커스텀 ref인가.** `refs/heads`·`refs/tags` 밖이라 브랜치도 태그도 아니다 — 웹 브랜치 목록에 안 뜨고, `ls-remote --heads`에 안 잡히고, 기본 clone/fetch가 안 가져온다(GitHub 실측). `main`은 마켓플레이스가 읽는 배포 브랜치이고 축은 그와 무관한 주기로 자라는 데이터라, 둘이 만나지 않는 것이 맞다. 로컬 store는 워킹트리가 있는 평범한 저장소라 손편집은 그대로 된다 — 숨는 건 원격 쪽뿐이다.

대가는 분명하다: **웹 UI에서 보거나 고칠 수 없고**, 기본 refspec을 쓰는 미러는 이 데이터를 안 따라온다. 접근 경로는 `axis-sync.sh` 하나다.

**저장 위치.** `~/.cache/wf/axis-store` (`WF_AXIS_STORE`로 변경). 플러그인 디렉토리에 두지 않는다 — 설치 캐시는 버전마다 새 디렉토리라 버전업 즉시 축이 고아가 된다.

**최초 1회.** ref가 아직 없으면 `axis-sync.sh init`이 씨앗 도메인으로 store를 만든다. **push는 하지 않는다** — 원격 쓰기는 명령이 따로다.

## 파일 형식

가상의 파생 도메인이다 — 부모 `frontend` 의 `style` 을 같은 id 로 덮어 질문만 바꾼다.

```json
{
  "schema": 1,
  "domain": "frontend-vue",
  "description": "Vue 3 화면 기능",
  "extends": ["frontend"],
  "axes": [
    { "id": "style",
      "when": "화면에 렌더링되는가",
      "ask": "시각 정의의 출처는 — 목업? 디자인 토큰? scoped 스타일로 둘 것과 전역으로 둘 것은?",
      "source_hint": "정적 목업, 디자인 파일 프레임, as-is SFC 의 <style> 블록",
      "closed_when": "치수·색·타이포·radius·간격이 값마다 출처와 함께 적혀 있다",
      "excluded_when": "정본에 이 화면이 없다는 것을 찾아본 뒤 적는다 — 어디를 봤는지와 확인 시점이 함께 들어간다",
      "added_by": "<이 파생 도메인에서 질문을 바꾸게 된 계기>" }
  ],
  "retired": [
    { "id": "analytics", "retired_by": "2026-09 — 트래킹이 플랫폼 레이어로 이동, 기능 정의에서 판단할 것이 없어짐" }
  ]
}
```

필수는 `schema`·`domain`·`description`·`axes`, 축의 필수는 `id`·`ask`·`added_by`이고 `when`·`source_hint`·`closed_when`·`excluded_when`이 선택이다. 판정 기준 둘은 스키마상 선택이지만 **비워 두면 그 축은 질문만 갖고 이동한다.** 스키마 원본은 store의 `axes/_schema.json`.

**`extends`** 는 한 단계 병합된다. 같은 id가 있으면 자식 것이 부모의 자리를 그대로 차지한다 — 파생 도메인이 공통 축을 베끼지 않고 질문만 바꿀 수 있다.

**`retired`** 는 뺀 축을 `axes` 밖에 둔다. 같은 배열에 남기면 켜진 축과 죽은 축을 매 실행마다 다시 갈라야 하고 그 판정은 언젠가 틀린다. 그렇다고 지우기만 하면 근거는 히스토리에만 남는데 **아무도 히스토리를 grep하지 않아** 같은 축이 몇 달 뒤 그럴듯한 얼굴로 다시 들어온다. 읽는 시점이 다르므로(회고가 축을 추가하기 직전에만 본다) 배열을 나눈다.

축에 심각도 구분은 두지 않는다. 검사의 차단/경고는 그 검사의 오탐 위험에 대한 판단이지만, 축의 존재는 **누가 그걸 봤는가**에 대한 것이라 경고로 낮춘다고 덜 위험해지지 않는다 — "경고 축"은 곧 안 보는 축이 된다. 해당 없으면 "해당 없음" 행을 쓴다. 그것도 못 할 상황이면 그 축 하나만 통과시키는 우회가 있지만 이유를 적어야 통한다 (`evidence-patterns.md`).

**무엇을 올리나.** 같은 종류의 다른 프로젝트에서도 같은 누락을 잡았을 축만 올린다. 이 저장소의 특정 모듈이나 이 팀만의 규칙은 프로젝트 `.claude/<플러그인>.spec.jsonc`에 남긴다 — 올리면 다른 프로젝트에서 영구히 "해당 없음"인 행이 된다.

씨앗으로 `frontend`(behavior·style·state·state-lifetime·contract·entry-path·defaults·responsive·a11y·i18n·permission·performance·reuse·security·recurring·scope)와 `backend-api`(contract·error-codes·authz·validation·transaction·idempotency·performance·observability·compat)가 들어 있다. `scope`는 다른 축 위에 얹히므로 — 다른 축이 정해져야 「이것」이 무엇인지 정해진다 — 목록 마지막에 둔다. 출발점일 뿐 완결된 목록이 아니다 — 위 네 출처로 매번 도출하고 회고로 채운다.

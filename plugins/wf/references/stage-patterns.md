# 단계 패턴 — 이음매와 위임

워크플로우를 스킬로 옮길 때 가장 중요한 판정은 **무엇을 스킬로 만들고 무엇을 만들지 않는가**다.

## 이음매만 스킬로 만든다

기존 스킬을 감싸기만 하는 스킬은 지시문을 한 겹 늘리고 원본의 품질을 희석한다. "`/tdd`를 실행하라"고만 적힌 스킬은 `/tdd`를 직접 부르는 것보다 나쁘다.

| 스킬로 만들 가치가 있다 | 만들지 않는다 |
|---|---|
| 도구 A의 출력을 도구 B의 입력으로 옮긴다 | 기존 스킬 하나를 그대로 호출한다 |
| 프로젝트 고유의 결정이 담긴다 (경로·규약·정책) | 일반적인 판단이라 기존 스킬이 이미 잘한다 |
| 증거를 만들고 기록하는 규약이 있다 | 산출물이 대화에만 남는다 |
| 여러 도구의 겹치는 기능 중 무엇을 쓸지 정해져 있다 | 도구가 하나뿐이다 |

## 흔한 단계와 그 형태

아래는 소프트웨어 개발 워크플로우에서 반복해 나타나는 단계다. 도메인이 다르면 이름과 개수가 달라지므로 그대로 쓰지 말고 참조만 한다.

| 단계 | 성격 | 이음매인가 | 걸 검증 |
|---|---|---|---|
| 부트스트랩 | 저장소를 워크플로우 전제 상태로 | ✓ 프로젝트 고유 | 존재 |
| 근거 수집 | 이미 정해진 것 / 안 정해진 것 분리 | ✓ 출처 규약 | 인용, 부정 |
| 정제 | 계획 압박 | ✗ `/grill-*`에 위임 | — |
| 정의·설계 | 무엇을 만들지 확정 | ✓ **축 커버리지** | 커버리지, 인용 |
| 정의 프리뷰 | 구현 전 누락 노출 | ✓ 프로젝트 고유 | 존재, 커버리지 |
| 명세 | 스펙 산출 | ✗ `/to-spec`에 위임 | — |
| 분해·적재 | 착수 단위로 쪼개 트래커에 | ✓ 트래커 규약 | 존재, 불변식 |
| 착수 | 고르기·claim·실행 환경 | ✓ 트래커↔실행 이음매 | 존재 |
| 구현 | 코드 작성 | ✗ `/implement`·`/tdd`에 위임 | 실행 |
| 검증 | 실제 동작 확인 + 증거 | ✓ 증거 저장 규약 | 실행, 존재 |
| 리뷰 | 코드 검토 | ✗ `/code-review`에 위임 | — |
| 마감 | 게이트·닫기·다음 제시 | ✓ 정책 (커밋 권한 등) | 실행, 불변식 |
| 핸드오프 | 세션 이관 | ✗ `long-run:session-handoff`에 위임 | — |
| 인테이크 | 외부 유입 적재 | ✓ 트래커 규약 | 존재, 인용 |
| 회고 | 재작업 원인 → 축 추가 | ✓ 스펙 갱신 | — |

`걸 검증` 칸의 이름은 스펙의 `stages[].checks` 에 적는 값과 대응한다(`evidence-patterns.md`). 인용·부정·커버리지를 건 단계는 산출물이 파일이어야 하고 스펙에 `artifact` 를 단다. 정의 프리뷰는 스펙에서 독립 단계가 아니라 정의 단계의 `preview` 키다(`preview-patterns.md`).

## 위임 대상 후보

이 표가 위임 대상의 정본이다. 다른 문서의 표는 여기를 옮긴 것이다.

이 표의 이름은 스킬의 이름이지 부르는 이름이 아니다. mattpocock 스킬군을 플러그인으로 설치했으면 `mattpocock-skills:tdd` 로, `npx skills add` 로 복사해 뒀으면 `tdd` 로 불린다 — Skill 도구도, 사용자가 치는 슬래시 명령도 같다. `scripts/check-deps.mjs` 가 이 기기에서 부르는 이름을 찍으므로 생성물에는 그 이름을 적는다. 맨이름을 적어 두면 플러그인으로 설치한 기기에서 「사용자에게 `/to-tickets` 를 쳐 달라」가 풀리지 않는다. **템플릿과 아래 문구 예시는 플러그인 이름으로 적혀 있다** — 권하는 설치 형태가 플러그인이기 때문이다. `check-deps` 가 「부르는 이름」을 찍지 않은 스킬(맨이름으로 설치된 것)은 생성물에서 `mattpocock-skills:` 접두를 뗀다.

설치돼 있으면 감싸지 않고 그 스킬에 맡긴다. 맡기는 문구는 모델이 그 스킬을 부를 수 있는지에 따라 갈린다(아래 「위임 단계의 문구」). 없으면 `find-skills`로 조사한다.

`scripts/check-deps.mjs` 가 설치 여부를 보는 것은 이 중 기본 스펙이 쓰는 mattpocock 스킬 13개와 `find-skills`·`agent-browser` 다. 표의 나머지 — `/grill-me`(코드베이스가 없을 때의 대안), `/retro` — 는 그 판단을 워크플로우에 넣기로 했을 때 design 4단계에서 설치 여부를 본다.

† 는 upstream 이 `disable-model-invocation: true` 로 둔 스킬이다(`mattpocock/skills` main `49dd158`, 2026-10-12 실측. `pstack` 은 0.15.36, 2026-11-13 실측 — 전부 †다). 모델이 Skill 도구로 부를 수 없고 사용자가 직접 쳐야 한다. 표시는 실측일의 사실이다 — 설계할 때는 설치본 `SKILL.md` 의 frontmatter 를 직접 본다.

| 판단 | 스킬 |
|---|---|
| 계획 압박 | `/grill-with-docs`†(코드베이스 있음), `/grill-me`† |
| 스펙 | `/to-spec`† |
| 이슈 분해 | `/to-tickets`† |
| 구현 | `/implement`†, `/tdd` |
| 리뷰 | `/code-review` |
| 버그 진단 | `/diagnosing-bugs` |
| 트리아지 | `/triage`† |
| 대형 작업 지도 | `/wayfinder`† |
| 리서치 | `/research` |
| 세션 이관 | `long-run:session-handoff` |
| 여러 세션에 걸친 실행 | `long-run:map-run` |
| 설계 질문 | `/prototype` |
| 도메인 용어 | `/domain-modeling` |
| 세션 회고 (에이전트 환경) | `/retro`† — 워크플로우의 재작업·누락은 `wf:retro` |
| 반복되는 실수를 강제 장치로 | `pstack:correct`† — 구조 → 타입 → 고칠 방법을 적은 lint → 테스트 → 문서 순으로 올린다 |
| 변경의 영향 범위 | `pstack:blast-radius`† — diff 밖에서 무엇이 깨지는지, 안전의 근거 하나를 실행으로 증명한다 |
| 성능 수치의 검증 | `pstack:benchmark-checklist`† — 측정한 숫자를 보고하거나 그것으로 고르기 전에 |
| 과제 문장을 깊게 다시 쓰기 | `pstack:sharpen`† |
| 브라우저 조작 | `agent-browser` |

## 위임 단계의 문구

위임 단계에는 스킬이 없다. 그 단계로 넘기는 문장은 **앞 이음매 스킬의 끝**과 `PRIME.md` 의 단계 순서에 놓이고, 무엇을 쓸지는 대상 스킬을 모델이 부를 수 있는지가 정한다.

| 대상 스킬 | 쓰는 문구 | 그 뒤 |
|---|---|---|
| 모델이 부를 수 있다 | 「Skill 도구를 `"mattpocock-skills:tdd"` 로 호출한다」 — 도구를 이름으로 적는다. 산문에 `/tdd` 만 두면 명령이 아니라 언급으로 읽힐 수 있다 | 같은 턴에서 이어 간다 |
| 사용자만 부를 수 있다(†) — 자기 인자·서브에이전트·`context: fork`·훅을 가진 스킬 | 「사용자에게 `/mattpocock-skills:implement <넘길 것>` 을 실행해 달라고 요청하고 턴을 끝낸다」 — 넘길 것(티켓 ID·문서 경로)과, 끝난 뒤 이어 부를 이음매 스킬을 함께 알린다 | 사용자가 친다. 워크플로우는 다음 이음매 스킬의 첫 동작(앞 단계 증거 확인)에서 다시 잡힌다 |
| 사용자만 부를 수 있다(†) — 본문이 지침뿐인 스킬 | 앞 이음매 스킬에 주입 블록을 둔다(아래 「경로 주입」). 블록의 `use: Read` 를 보고 `path:` 의 `SKILL.md` 를 읽어 따른다 | 같은 턴에서 이어 간다 |

† 스킬을 Skill 도구로 부르라고 쓰면 그 호출은 거부된다(`cannot be used with Skill tool due to disable-model-invocation`).

사용자만 부를 수 있는 단계가 연달아 오면(정제 → 명세) 그 사이에는 이음매 스킬이 없다. 그 순서를 알리는 것은 `PRIME.md` 다 — 단계 순서에서 위임 단계를 빼지 않고, 사용자가 치는 것을 표시한다. 이 문구를 싣기 위해 감싸는 스킬을 만들지 않는다.

upstream 도 같은 규약을 쓴다(`mattpocock/skills` 의 `.agents/invocation.md`).

### 경로 주입

† 스킬을 Skill 도구로 부를 수는 없지만 파일로 읽을 수는 있다. 읽으면 지침은 오고 **실행 의미는 오지 않는다** — 그 스킬의 인자 치환, `allowed-tools`, 모델·fork 설정, 훅이 빠진다. 그래서 본문이 지침뿐인 스킬에만 쓴다. `pstack` 은 자기 문서(`docs/harness/claude-code.md`)가 Claude Code 에서 이 방식을 쓰라고 적는다.

설치 위치는 기기마다 다르므로 경로를 본문에 적지 않는다. 스킬이 로드될 때 스크립트가 찾아 싣는다:

```markdown
---
allowed-tools: Bash(node "${CLAUDE_PLUGIN_ROOT}/scripts/resolve-skill.mjs" *)
---

<delegate-skill>
!`node "${CLAUDE_PLUGIN_ROOT}/scripts/resolve-skill.mjs" pstack:blast-radius --install "<없을 때 알릴 설치 방법>"`
</delegate-skill>
```

출력의 첫 줄이 `FOUND` 면 `path:`·`origin:`·`use:` 가 따라오고, `MISSING` 이면 `install:` 이 따라온다. `use:` 는 대상의 frontmatter 를 읽어 정해진다 — upstream 이 제한을 풀면 `use: Skill` 로 바뀌므로 본문은 「`use:` 줄대로 한다」고만 쓴다. `allowed-tools` 의 그 줄이 없으면 로드 때 치환되지 않고 「이 명령을 먼저 실행하라」는 지시로 바뀐다. 맨이름으로 물을 때는 `--from <플러그인>` 을 함께 준다 — 같은 이름의 스킬을 여러 플러그인이 낸다(`tdd` 는 `mattpocock-skills` 와 `pstack` 에 둘 다 있다). 찾는 순서는 프로젝트 → `~/.claude/skills` → `~/.agents/skills` → 플러그인 설치본이고, 묻는 쪽 플러그인 자신의 스킬은 후보가 아니다(`scripts/lib/skill-locate.mjs`).

남의 스킬의 본문을 이음매 스킬에 옮겨 적지 않는다. 사본은 upstream 이 나아져도 그대로 남는다.

## 단계 사이의 계약

각 단계는 앞 단계의 증거를 입력으로 받고 자기 증거를 남긴다. 증거가 없으면 시작하지 않는다.

```
단계 N   산출물 + 증거 경로  →  단계 N+1 의 첫 동작: 그 증거를 확인
```

이 계약이 없으면 단계는 순서일 뿐 검문소가 아니다.

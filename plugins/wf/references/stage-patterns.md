# 단계 패턴 — 이음매와 위임

워크플로우를 스킬로 옮길 때 가장 중요한 판정은 **무엇을 스킬로 만들고 무엇을 만들지 않는가**다.

## 이음매만 스킬로 만든다

기존 스킬을 감싸기만 하는 스킬은 지시문을 한 겹 늘리고 원본의 품질을 희석한다. "`/tdd`를 실행하라"고만 적힌 스킬은 `/tdd`를 직접 부르는 것보다 나쁘다.

| 스킬로 만들 가치가 있다 | 만들지 않는다 |
|---|---|
| 도구 A의 출력을 도구 B의 입력으로 옮긴다 | 기존 스킬 하나를 그대로 호출한다 |
| 프로젝트 고유의 결정이 담긴다 (경로·규약·정책) | 일반적인 판단이라 기존 스킬이 이미 잘한다 |
| 증거를 만들고 기록하는 규약이 있다 | 산출물이 대화에만 남는다 |
| 여러 도구의 겹치는 기능 중 무엇을 쓸지 정해져 있다 | 도구가 하나뿐이다 |

## 흔한 단계와 그 형태

아래는 소프트웨어 개발 워크플로우에서 반복해 나타나는 단계다. 도메인이 다르면 이름과 개수가 달라지므로 그대로 쓰지 말고 참조만 한다.

| 단계 | 성격 | 이음매인가 | 걸 검증 |
|---|---|---|---|
| 부트스트랩 | 저장소를 워크플로우 전제 상태로 | ✓ 프로젝트 고유 | 존재 |
| 근거 수집 | 이미 정해진 것 / 안 정해진 것 분리 | ✓ 출처 규약 | 인용, 부정 |
| 정제 | 계획 압박 | ✗ `/grill-*`에 위임 | — |
| 정의·설계 | 무엇을 만들지 확정 | ✓ **축 커버리지** | 커버리지, 인용 |
| 정의 프리뷰 | 구현 전 누락 노출 | ✓ 프로젝트 고유 | 존재, 커버리지 |
| 명세 | 스펙 산출 | ✗ `/to-spec`에 위임 | — |
| 분해·적재 | 착수 단위로 쪼개 트래커에 | ✓ 트래커 규약 | 존재, 불변식 |
| 착수 | 고르기·claim·실행 환경 | ✓ 트래커↔실행 이음매 | 존재 |
| 구현 | 코드 작성 | ✗ `/implement`·`/tdd`에 위임 | 실행 |
| 검증 | 실제 동작 확인 + 증거 | ✓ 증거 저장 규약 | 실행, 존재 |
| 리뷰 | 코드 검토 | ✗ `/code-review`에 위임 | — |
| 마감 | 게이트·닫기·다음 제시 | ✓ 정책 (커밋 권한 등) | 실행, 불변식 |
| 핸드오프 | 세션 이관 | ✗ `long-run:session-handoff`에 위임 | — |
| 인테이크 | 외부 유입 적재 | ✓ 트래커 규약 | 존재, 인용 |
| 회고 | 재작업 원인 → 축 추가 | ✓ 스펙 갱신 | — |

`걸 검증` 칸의 이름은 스펙의 `stages[].checks` 에 적는 값과 대응한다(`evidence-patterns.md`). 인용·부정·커버리지를 건 단계는 산출물이 파일이어야 하고 스펙에 `artifact` 를 단다. 정의 프리뷰는 스펙에서 독립 단계가 아니라 정의 단계의 `preview` 키다(`preview-patterns.md`).

## 위임 대상 후보

이 표가 위임 대상의 정본이다. 다른 문서의 표는 여기를 옮긴 것이다.

설치돼 있으면 감싸지 않고 그 스킬에 맡긴다. 맡기는 문구는 모델이 그 스킬을 부를 수 있는지에 따라 갈린다(아래 「위임 단계의 문구」). 없으면 `find-skills`로 조사한다.

`scripts/check-deps.mjs` 가 설치 여부를 보는 것은 이 중 기본 스펙이 쓰는 mattpocock 스킬 13개와 `find-skills`·`agent-browser` 다. 표의 나머지 — `/grill-me`(코드베이스가 없을 때의 대안), `/retro` — 는 그 판단을 워크플로우에 넣기로 했을 때 design 4단계에서 설치 여부를 본다.

† 는 upstream 이 `disable-model-invocation: true` 로 둔 스킬이다(`mattpocock/skills` main `49dd158`, 2026-10-12 실측). 모델이 Skill 도구로 부를 수 없고 사용자가 직접 쳐야 한다. 표시는 실측일의 사실이다 — 설계할 때는 설치본 `SKILL.md` 의 frontmatter 를 직접 본다.

| 판단 | 스킬 |
|---|---|
| 계획 압박 | `/grill-with-docs`†(코드베이스 있음), `/grill-me`† |
| 스펙 | `/to-spec`† |
| 이슈 분해 | `/to-tickets`† |
| 구현 | `/implement`†, `/tdd` |
| 리뷰 | `/code-review` |
| 버그 진단 | `/diagnosing-bugs` |
| 트리아지 | `/triage`† |
| 대형 작업 지도 | `/wayfinder`† |
| 리서치 | `/research` |
| 세션 이관 | `long-run:session-handoff` |
| 여러 세션에 걸친 실행 | `long-run:map-run` |
| 설계 질문 | `/prototype` |
| 도메인 용어 | `/domain-modeling` |
| 세션 회고 (에이전트 환경) | `/retro`† — 사용자가 직접 실행한다. 워크플로우의 재작업·누락은 `wf:retro` |
| 브라우저 조작 | `agent-browser` |

## 위임 단계의 문구

위임 단계에는 스킬이 없다. 그 단계로 넘기는 문장은 **앞 이음매 스킬의 끝**과 `PRIME.md` 의 단계 순서에 놓이고, 무엇을 쓸지는 대상 스킬을 모델이 부를 수 있는지가 정한다.

| 대상 스킬 | 쓰는 문구 | 그 뒤 |
|---|---|---|
| 모델이 부를 수 있다 | 「Skill 도구를 `"tdd"` 로 호출한다」 — 도구를 이름으로 적는다. 산문에 `/tdd` 만 두면 명령이 아니라 언급으로 읽힐 수 있다 | 같은 턴에서 이어 간다 |
| 사용자만 부를 수 있다(†) | 「사용자에게 `/implement <넘길 것>` 을 실행해 달라고 요청하고 턴을 끝낸다」 — 넘길 것(티켓 ID·문서 경로)과, 끝난 뒤 이어 부를 이음매 스킬을 함께 알린다 | 사용자가 친다. 워크플로우는 다음 이음매 스킬의 첫 동작(앞 단계 증거 확인)에서 다시 잡힌다 |

† 스킬을 Skill 도구로 부르라고 쓰면 그 호출은 거부된다(`cannot be used with Skill tool due to disable-model-invocation`).

사용자만 부를 수 있는 단계가 연달아 오면(정제 → 명세) 그 사이에는 이음매 스킬이 없다. 그 순서를 알리는 것은 `PRIME.md` 다 — 단계 순서에서 위임 단계를 빼지 않고, 사용자가 치는 것을 표시한다. 이 문구를 싣기 위해 감싸는 스킬을 만들지 않는다.

upstream 도 같은 규약을 쓴다(`mattpocock/skills` 의 `.agents/invocation.md`).

## 단계 사이의 계약

각 단계는 앞 단계의 증거를 입력으로 받고 자기 증거를 남긴다. 증거가 없으면 시작하지 않는다.

```
단계 N   산출물 + 증거 경로  →  단계 N+1 의 첫 동작: 그 증거를 확인
```

이 계약이 없으면 단계는 순서일 뿐 검문소가 아니다.

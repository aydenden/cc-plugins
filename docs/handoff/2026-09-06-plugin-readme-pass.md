## 배경 — 무엇을 위한 문서인가

이 레포는 개인 퍼블릭 레포이자 **프론트엔드 채용 면접관이 볼 포트폴리오**다. 목표는
"능동적이고 능률적으로 일한다"를 주장이 아니라 증거로 보이는 것. 그래서 루트 README 는
목록형 표를 걷어내고 플러그인마다 **계기 → 설계 판단 → 포기한 것 → 구성** 순으로 다시 썼다.

톤 방침(루트에서 확정, 하위에도 적용):
- 계기 한 줄만 1인칭(주어 생략), 설계 판단은 3인칭
- 포기한 것과 트레이드오프를 명시한다. 이게 신뢰를 산다
- 회사·조직·사내 도구를 절대 언급하지 않는다 (스택명도 특정하지 않는다 — Angular 만
  적으면 React 회사에서 감점 위험, 그리고 wf 의 "스택 비종속" 주장과도 모순된다)

## 할 일

### 1. llm-wiki — 설치 절이 없다 (셋 중 유일)
루트 README 카드에서 링크를 타고 온 독자가 설치법을 찾지 못한다. `## 볼트 경로`(20행)
앞이나 뒤에 짧게 추가한다. 전제 조건은 `WIKI_PATH` 또는 `OBSIDIAN_VAULT_PATH` 환경변수와
볼트 루트의 `SCHEMA.md`. 다른 두 README 의 `## 설치` 형식을 따른다.

### 2. wf — 설치 절의 진입 장벽 (59~112행, 전체의 40%)
`npx skills add` 가 13줄 연속으로 나열돼 실제보다 문턱이 높아 보인다. 필수/조건부/위임
구분은 이미 있으니 **위임 대상 13개를 접거나(`<details>`) 한 줄로 합치는** 정도로 충분하다.
내용을 지우지는 말 것 — 의존성을 정확히 밝히는 것이 이 레포의 방침이다.

### 3. wf — "검토 축" 설명이 추상적 (21~29행)
독자 테스트에서 나온 지적: *"축 설명이 추상적 서술이라 무엇을 실제로 검사하는지 손에 안
잡힌다."* `scripts/check-coverage.sh` 가 무엇을 세는지, 축 하나가 실제로 어떻게 생겼는지
(예: `templates/axis-store/` 의 frontend 축) 한 줄 예시를 넣으면 해소된다.

### 4. memory-guard — 구조 절 재확인 (104~124행)
2026-09-06 에 OpenCode 지원을 제거하며 이 절을 새로 썼다. 앞뒤 흐름이 자연스러운지,
`## 설치`(87행) → `## 구조`(104행) 순서가 맞는지 한 번 읽어볼 것.

## 1. 목적과 판정 기준

구매한 기술서 PDF와 웹 문서를 마크다운으로 바꿔 Obsidian 볼트(`$WIKI_PATH`)에 넣는다.
목표는 CC가 통째로 읽고 검색할 수 있는 형태다.

**판정 기준 3항목** (하나라도 무너지면 도구 교체):

1. 코드블록이 살아 있나 — 언어 표시까지는 안 바라도 **블록 경계**가 남았나
2. 표가 뭉개지지 않았나
3. 헤딩이 `#` 계층으로 남아 **챕터 경계가 깨끗하게 잘리나**

**절대 조건**: 구매한 저작물이므로 **로컬 실행(에어갭)**. 책 본문은 어떤 저장소에도 커밋하지 않는다.

| 항목 | 실측값 |

| 페이지 | 462p |
| 파일 크기 | 233.8 MB (페이지당 ~500KB) |

## 3. 판정 결과

### 3.1 종합

| 판정 항목 | docling (기본 파이프라인) | **marker** |
|---|---|---|
| ① 코드블록 | **실패** | **통과** |
| ② 표 | 미검증(구간에 표 없음) | **통과** |
| ③ 헤딩 | **실패** | **통과** |

**결론: 책은 marker, 웹은 docling.**

docling의 실패는 도구 자체의 결함이라기보다 **텍스트 레이어 없는 열화 스캔본**이라는 입력 조건 탓이 크다.
텍스트 레이어가 살아있는 PDF에서 docling이 어떤지는 **검증하지 않았다** — 단정하지 말 것.

### 3.3 docling이 무너진 방식

코드블록 — 펜스는 생겼으나 내용이 파괴됨:

```
I/ base case for (int i= 0; i 《= n; itt) dp[i][0] = 1; for (int i= 1; i <=n; itt) {
```

- 줄바꿈 전소실 → 코드 전체가 한 줄
- **산문이 코드펜스 안에 혼입** ("또한 dp 배열의 전이는…")
- 코드 다수가 펜스 **밖** 평문으로 흩어짐
- OCR 오독 광범위: `itt`←`i++`, `jtt`←`j++`, `《=`←`<=`, `1/`←`//`, `J else`←`} else`,
  `coins[1-1]`←`coins[i-1]`, `dp[i][i]`←`dp[i][j]`, `!= 1`←`!= -1`, `.Length`←`.length`

헤딩 — 승격된 4개가 **전부 본문 문장 또는 도표 숫자**:

```
## 대표적이고 기술적인 동적 계획법 문제다. 길에 늘어선 집들을 …
## 0 2 3 4 6
```

실제 절 제목 `2.18.1 선형 배열`은 평문으로 남음 → **분할 가능한 헤딩 0개**.

추가 붕괴 (원본 지면과 대조):

- **읽기 순서 오류** — 각주와 페이지 푸터가 본문 한복판에 삽입됨
- **블록 병합 오류** — 서로 다른 문단이 한 줄로 합쳐짐.
  원본 「각 요소 nums[i]는 **i번째 집의 현금 액수를 나타낸다**」 + 별개 문단 「**문제는 이해하기 쉽고**…」
  → `각 요소 nums[i]는 1번째 문제는 이해하기 쉽고`
- **머리말/꼬리말 미분리** — `202 CHAPTER 2 동적 계획법`이 본문으로 취급됨

> **주의**: 초기에 이를 "2단 조판 붕괴"로 진단했으나 **오진이었다.** 지면 렌더 결과 이 책은 전부 1단이다.
> 1단인데도 무너졌다는 건 조판 난이도 탓이 아니라 **스캔 이미지에서 블록 경계를 못 잡는다**는 뜻이라 더 나쁜 신호다.

### 3.4 marker가 통과한 방식

헤딩 — 원본 지면과 대조하여 정확 확인:

```
## 2.18 문제는 변해도 방법은 변하지 않는다
### 2.18.1 선형 배열
## 2.18.2 원형 배열
### 2.18.3 트리 배열
## 2.19 동적 계획법과 역추적 알고리즘의 관계
### 2.19.1 역추적 아이디어
```

코드 — 들여쓰기·문법 보존:

```java
int dp(int[] nums, int start) {
    if (start >= nums.length) {
        return 0;
    }
```

`i++`, `//`, `>=`, `nums.length`, `Arrays.fill(memo, -1)` 전부 정확.

표 (원본: 3열 × 30행, 컬러 배경, **병합 셀 포함**):

- 3열 구조 유지, 쪽수 전부 원본 일치
- **두 줄로 접힌 긴 URL이 한 줄로 복원됨**: `serialize-and-deserialize-binary-` + `tree/` → 정상 결합
- **병합 셀**은 첫 칸을 비운 행으로 처리 (마크다운 한계 내 타당)

다이어그램 — 별도 JPEG로 크롭 추출, 본문엔 `![](_page_181_Diagram_7.jpeg)` 링크.
잘라낸 이미지에 라벨 `s`/`p`/`i`/`j`/`j+2`와 문자 전부 온전.

### 3.5 marker의 남은 결함 (실패는 아니나 기록)

- 코드블록 하나가 둘로 쪼개지며 중괄호 오배치: `}int res = Math.max(` → **읽기엔 지장 없으나 복사해 컴파일 불가**
- 코드 식별자가 수식으로 변환: `nums[start]` → `$nums[start]$`
- 리스트 번호 중복: `1. 1. 만약…`
- **본문 문장을 헤딩으로 오승격**: `## 2-2 \* 와일드카드가 없으면 일치할 수 없으므로 실패를 의미한다.`
- 코드펜스에 언어 표시 없음 (판정상 허용 범위)

### 3.6 웹 검증 (docling, MDN `grid-template-areas`)

| 항목 | 값 |
|---|---|
| 소요 | **0.24초** (변환) / 4.9초 (기동 포함) |
| 산출 | 110 KB · 1,563줄 |
| 헤딩 | `#`→`##`→`###`→`####` **계층 정확** |
| 코드블록 | 8개, 경계 온전 (언어 표시 없음) |
| 표 | 1개 정상 마크다운 표 |

`docling convert <URL>` 한 줄로 처리된다. 별도 크롤러 불필요.

> **한계**: `## Formal definition`, `## Browser compatibility`는 **제목만 있고 내용이 빔**.
> MDN이 이 표들을 JS로 렌더링하므로 정적 HTML에 없고, docling은 브라우저를 띄우지 않는다.
> **동적 렌더링 사이트에는 구조적으로 못 미친다.** 필요하면 별도 수단이 필요하다.

## 4. 아키텍처 결정 (ADR)

### ADR-1: 책 변환 = `marker-pdf` (Apache-2.0)

판정 3항목 통과. docling 기본 파이프라인은 ①③ 실패.

### ADR-2: 웹 변환 = `docling` (MIT)

0.24초에 헤딩·코드·표 정상. URL 직접 입력 지원으로 별도 크롤러 불필요.
**단 JS 렌더링 표는 못 가져온다.**

### ADR-3: OCR 엔진

- docling: `ocrmac`(Apple Vision) 별도 설치 필요 — `uv tool install --python 3.12 docling --with ocrmac`
- marker: 자체 `surya` VLM 사용, 별도 설치 불필요

### ADR-4: LLM 교정을 쓰지 않는다

marker의 `--use_llm`은 채택하지 않는다. 근거는 §5.

### ADR-5: 제외한 도구

| 도구 | 제외 사유 |
|---|---|
| `markitdown` | 복잡한 PDF에 취약 (사전 결정) |
| `MinerU` | 라이선스 **NOASSERTION** |
| `GOT-OCR2.0` | **라이선스 없음** |
| `zerox` / `nougat` | 1년 이상 정체 (최종 푸시 2025-05 / 2025-02) |

### ADR-6: 저장 구조 — 책 1권 = 폴더 1개

```
$WIKI_PATH/raw/books/<책이름>/
    00-toc.md          ← 목차 + 챕터 링크. 읽는 쪽의 진입점
    01-<챕터제목>.md
    02-<챕터제목>.md
```

**근거(산술)**: 300~400p 기술서 ≈ 700~900KB · 1.5만~2.5만 줄.
한 파일이면 Read 기본 2,000줄 상한에 걸려 통째로 못 읽는다. 챕터 단위면 20~60KB·500~1,500줄이라 한 번에 읽힌다.

**marker 실측 기준 재계산**: 9p → 12.7KB = **1.41KB/페이지**. 462p ≈ **651KB** (이미지 제외).
챕터당 평균 크기는 전체 변환 후 실측할 것 — 현재는 미실측.

## 5. OCR 오독 대응 — LLM을 쓰지 않는 이유

### 5.1 오독 실측 (marker 산출물 19페이지 · 564줄)

| 대상 | 검출 |
|---|---|
| URL 안 대문자 (확실한 오독) | `leetcode.com/problems/Iru-cache`, `.../Ifu-cache` — **2건** |
| 소문자 사이 대문자 `I` 토큰 | `Iru` 3건, `Ifu` 3건, `Integer` 1건(정상) |
| **코드블록 23개 · 245줄** | |
| ├ `i++` 오독 (`itt`/`1++`) | **0건** |
| ├ 주석 `//` 오독 (`1/`) | **0건** |
| ├ `.Length` 대문자 | **0건** |
| ├ `<=` 오독 (`《`) | **0건** |
| └ 중괄호 균형 | `{` 42 vs `}` 41 → **1건 불일치** |

**본문 오독은 사실상 `lru`/`lfu` 두 단어뿐이고, 코드 내 글자 오독은 0건이다.**
유일한 코드 결함은 오독이 아니라 §3.5의 블록 분할 오류다.

### 5.2 marker의 LLM 교정 기능 — 조사 결과 부적합

`--use_llm` + `--block_correction_prompt`로 LLM 교정이 가능하다.
`LLMPageCorrectionProcessor`는 `converters/pdf.py:107`의 **기본 프로세서 목록에 포함**돼 있어 `--use_llm`만 켜면 동작한다.

교정 가능 범위 (`processors/llm/llm_page_correction.py:54-56`): 읽기 순서 재정렬, 블록 타입 변경, HTML 수정.
`BLOCK_MAP`에 `"Code": ["pre"]`가 있어 코드 블록도 대상.

**그러나 이 문제에는 맞지 않는다:**

```python
# processors/llm/llm_page_correction.py:152
image = page1.get_image(document, highres=False)
```

- **페이지 전체를, 저해상도로** 보낸다. `l`과 `I`를 구분하려면 획이 선명해야 하는데 **원본보다 흐릿한 그림**을 모델이 본다
- 이 프로세서는 읽기 순서·블록 타입 교정용이지 **글자 단위 오독 교정용이 아니다**

**크롭 경로는 존재하지만 블록 단위까지다:**

| 계열 | 보내는 것 | 해당 프로세서 |
|---|---|---|
| `BaseLLMSimpleBlockProcessor` | **블록만 크롭**, `highres=True` | 수식, 필기, 그림설명, 복잡영역 |
| `BaseLLMComplexBlockProcessor` | 자체 로직 (페이지교정은 저해상도 페이지 전체) | 표, 표병합, 섹션헤더, 수학블록, 페이지교정 |

**단어 단위 크롭 교정은 없다.** 근본 이유: marker는 **자기가 어디를 틀렸는지 모른다.** 오독 위치를 알아야 크롭할 텐데, 그걸 알면 이미 고칠 수 있다.

**에어갭 문제도 있다:**

| LLM 서비스 | 책 내용 외부 전송 |
|---|---|
| Gemini(기본) · Claude · OpenAI · Azure · OpenRouter · Vertex | **전송됨** |
| **Ollama** | 로컬 |

에어갭 조건상 Ollama가 유일 선택지인데:
- `ollama` 바이너리는 설치돼 있음 (`/opt/homebrew/bin/ollama`), 서버는 미기동
- **보유 모델 0개** (`~/.ollama/models` 8KB) → 비전 모델 3~8GB 다운로드 필요
- marker 기본 ollama 모델은 `gemma3` (`services/ollama.py:19`)
- 페이지마다 LLM 호출 추가 → 462p 작업이 **하룻밤 단위**로 늘어남
- LLM이 원문을 "고치는" 것이라 **잘못 고칠 새 위험**이 생김

### 5.3 채택 방침: 규칙 기반 후처리

실측된 오독이 두 단어뿐이므로 LLM이 불필요하다. 규칙 2개로 충분:

1. `leetcode.com/problems/<slug>`의 slug는 **전부 소문자** → 대문자가 있으면 무조건 오독
2. 용어 사전 대조: `Iru`→`lru`, `Ifu`→`lfu` (`Integer` 등 정상 단어는 사전에 없으니 미변경)

시간 비용 사실상 0, 결정론적, 재현 가능.

**한계 (반드시 인지)**: 이 방식은 **알려진 오독만** 잡는다. 처음 보는 오독은 못 잡는다.
표본이 **462p 중 19p = 4%**에 불과하므로 전체가 이렇게 깨끗하리라는 보장은 없다.

### 5.4 자동 검사기 (구현 대상)

| 검사 | 검출력 | 19p 실적 |
|---|---|---|
| 코드블록 중괄호 균형 | 확정적 | **1건 검출** |
| URL 내 대문자 | 확정적 (slug 규칙) | **2건 검출** |
| 용어 사전 대조 | 사전 등재분만 | 6건 |

### 5.5 CC가 읽을 때 오탈자를 잡아주는가 — 의존 금지

**부분적으로 잡지만 안전망이 아니다.**

- 맥락이 강하면 잡는다 (실제로 이 세션에서 docling의 `itt`·`1/`·`《=`를 즉시 지목)
- **더 위험한 습성**: LLM은 `Iru`를 자동으로 `lru`로 해석하고 **조용히 넘어간다.**
  답변에는 지장이 없으므로 **사용자는 원문이 틀렸다는 걸 영영 모른다.** URL을 복사해 넣었을 때 404로 발견된다
- **맥락으로 복원 불가한 유형은 못 잡는다**:

| 유형 | 예 | 왜 못 잡나 |
|---|---|---|
| 배열 인덱스 | `dp[i][j]` → `dp[i][i]` | 둘 다 문법상 정상 |
| 상수·경계값 | `start + 2` → `start + 1` | 여전히 말이 됨 |
| 숫자 | 쪽수 `207` → `201` | 검증 근거 없음 |
| 변수명 | `memo` → `memq` | 일관되면 그런 이름인 줄 앎 |

알고리즘 책에서 **인덱스 하나가 정답과 오답을 가른다.** 그럴듯해 보이므로 LLM이 자신 있게 틀린 설명을 할 수 있다.

**대책:**

1. **원본 PDF를 버리지 않는다.** 마크다운은 검색·탐색용, 최종 심급은 원본
2. **각 챕터 파일에 원본 페이지 범위 주석**을 남긴다: `<!-- 원본: PDF p.224-232 -->`. marker JSON에 페이지 정보가 있으므로 분할 스크립트에서 자동 삽입 가능
3. **`00-toc.md` 맨 위에 경고를 박는다.** 나중 세션의 CC가 먼저 읽는다:

   > 이 자료는 스캔본 OCR 산출물이다. 코드의 인덱스·상수·변수명에 오독 가능성이 있다.
   > 코드를 인용하거나 동작을 단정하기 전에 원본 PDF 해당 페이지를 확인할 것.
   > 이상한 토큰을 발견하면 **조용히 고쳐 읽지 말고 사용자에게 알릴 것.**

## 6. 챕터 분할 — 함정 2개

**`^## ` 로 자르면 안 된다.** 실측으로 확인된 오탐:

1. marker가 본문 문장을 헤딩으로 오승격: `## 2-2 \* 와일드카드가 없으면 일치할 수 없으므로…`
2. 코드블록 **안의** `#` 시작 줄 — MDN 산출물에 CSS 선택자 `#page`, `#example-element`가 실재

**대응**: `^##+ \d+\.\d+` 처럼 **절 번호를 요구**하는 패턴을 쓰거나, marker의 **JSON 출력**(`--output_format json`)에서 블록 타입 `SectionHeader`를 기준으로 자른다. JSON 경로가 더 안전하다.

## 7. 볼트 적재 규약 (`$WIKI_PATH`)

볼트 루트 `SCHEMA.md` 실측 확인 결과:

- **`raw/`는 `index.md` 등재 대상이 아니다** — `index.md` 내 `raw/` 참조 **0건**으로 확인 (추정 아님)
- **`raw/` 전용 frontmatter가 강제된다**:

```yaml
---
source_url: https://example.com/article   # 해당 시
ingested: YYYY-MM-DD
sha256: <프론트매터 제외 본문의 해시>
---
```

  `sha256`은 재ingest 시 변경 감지·스킵용. **본문만** 대상으로 계산.
- **`log.md`에 작업 기록 한 줄 추가**가 규약 (`Every action must be appended to log.md`)
- 위키 페이지(`concepts/` 등)와 달리 raw는 태그 택소노미·최소 2개 아웃바운드 링크 규칙 대상이 아님

> **미결**: 책 1권이 수십 개 파일이므로 `log.md`에 파일마다 한 줄씩 쓸지, **책 단위로 한 줄**만 쓸지 정해야 한다. 후자를 권한다.

> **미결 (통합 지점)**: 이 파이프라인을 llm-wiki 플러그인의 어디에 붙일지.
> 후보 — (a) `/llm-wiki:capture` 확장, (b) 신규 `/llm-wiki:ingest-book` 커맨드, (c) 독립 스크립트로 두고 스킬에서 호출.
> 책 변환은 시간이 오래 걸리고(1.3~2h) 대화형 흐름과 성격이 달라 **(b) 또는 (c)를 권한다.**

## 9. 함정 모음 (다음 세션이 반드시 볼 것)

1. **페이지 번호 기준이 다르다** — **marker는 0-indexed, docling은 1-indexed.**
   marker 이미지 파일명(`_page_225_...`)과 원본 지면 대조로 확인. 스크립트에서 어긋나기 쉬운 지점
2. **docling 기본 출력은 이미지를 base64로 본문에 인라인한다** — 9페이지 md가 432KB가 되고 그중 420KB가 이미지.
   `--image-export-mode placeholder`로 회피
3. **도서 폴더는 클라우드 동기화 폴더다** (`~/Library/CloudStorage/MYBOX-.../도서/`, 280권).
   **폴더 전체를 훑으면 미다운로드 파일의 다운로드가 트리거된다.** 이 세션에서 실제로 발생시켜 중단했다.
   **반드시 지정된 파일만 접근할 것**
4. **`--use_llm` 계열은 기본적으로 외부 API(Gemini)로 나간다.** 에어갭 위반. 켤 거면 반드시 `--llm_service=marker.services.ollama.OllamaService`
5. **marker 최초 실행은 모델 로딩 고정비가 크다** (9p 342.7s vs 10p 161.6s). 성능 측정 시 첫 실행 수치를 쓰지 말 것

## 부록 B: 재현용 명령

```bash
# 스캔 PDF 진단 (텍스트 레이어 유무)
pdfinfo "책.pdf"
pdftotext -f 1 -l 10 "책.pdf" - | wc -c     # 0에 가까우면 스캔본

# 책 변환 (marker, 0-indexed)
marker_single "책.pdf" --force_ocr \
  --output_format markdown --output_dir ./out

# 구조 보존이 필요하면 JSON 병행 (분할용)
marker_single "책.pdf" --force_ocr --output_format json --output_dir ./out

# 웹 변환 (docling, 1-indexed)
docling convert "https://example.com/doc" \
  --to md --image-export-mode placeholder --output ./out

# 참고: docling으로 스캔 PDF (판정 실패했으나 재현용)
docling convert "책.pdf" --page-range 224-232 \
  --ocr --ocr-engine ocrmac --ocr-lang ko-KR,en-US \
  --to md --output ./out
```
